# План реализации desktop Edizora

Дата: 2026-10-28. Основной документ: [ТЗ](desktop-app-spec.md). Все пункты ниже — предстоящая работа.

## Этапы и контрольные результаты

| Этап | Работа | Условие завершения |
| --- | --- | --- |
| 0. Базовая линия | Инвентаризация экранов/API, запуск существующих проверок, замеры текущего UI, fixture dataset | Матрица сценарий → endpoint → тест; сохранены исходные результаты и известные проблемы |
| 1. Вертикальный прототип | Tauri + bundled React + headless Python; bootstrap, login, чтение, mutation, upload/media | Один экран работает в установленной сборке без браузера; повторный запуск не создаёт второго host; измерены старт и память |
| 2. Надёжная оболочка | Single-instance, tray, завершение, reconnect, автозапуск, file dialogs, подготовка обновления | Проверены close-to-tray, drain, авария shell/backend, сон/возврат и первый запуск |
| 3. Основа frontend | Transport adapters, Router, Query, общие tokens/компоненты, loading/error, темы и доступность | Desktop и web используют общий UI; same-origin web auth не сломан; нет второго cache серверных данных |
| 4. Основной workflow | Публикации, редактор, загрузка, preview, recovery draft, очередь и календарь | Полный сценарий подготовки и планирования проходит на fixture backend; проверки конфликтов и idempotency |
| 5. Функциональный паритет | AI, каналы, настройки, диагностика, backup/restore, размещение | У каждого существующего сценария есть новый путь и регрессионная проверка |
| 6. Производительность | Большие списки, thumbnail pipeline, lazy chunks, polling/idle, профилирование | Отчёт с сырыми замерами и всеми бюджетами ТЗ; нет необъяснённых регрессий |
| 7. Установщик и приёмка | Воспроизводимая сборка, WebView2, upgrade/uninstall/reinstall, документация | Проверен installer на чистой Windows VM без dev-инструментов, подготовлены hashes и release notes |

Этап 1 — обязательный технический барьер до массовой переделки экранов. Если transport/media или размер/скорость не отвечают требованиям, сначала устранить причину и обновить архитектурную запись. Не менять стек молча. Срок в днях без прототипа не обещать; после этапа 1 оценить оставшиеся работы по фактическим рискам.

## Предлагаемая структура

```text
frontend/src/
  app/                 # bootstrap, router, providers
  features/            # publications, editor, queue, calendar, ai, settings...
  shared/api/          # generated types, transport, query keys
  shared/ui/           # компоненты и design tokens
  platform/            # desktop/web adapters
frontend/src-tauri/    # Rust shell, capabilities, lifecycle, bridge
app/desktop/          # headless bootstrap, setup, существующие сервисы
deploy/               # сборка sidecar + shell + Inno Setup
tests/                # backend, migration, bundle/installer
frontend/tests/       # UI и browser integration
desktop-tests/        # установленное Windows-приложение
```

Модули переносить по мере миграции, без единовременного переименования всего проекта. Временные адаптеры удалять после паритета и проверок соответствующего сценария.

## Матрица приёмки

| Сценарий | Проверка |
| --- | --- |
| Первая установка / legacy import / restore | Каждый путь завершает настройку в окне; прерывание не повреждает исходные данные |
| Повторный запуск | Одно окно/трей/host/runtime; проверка конкурирующих запусков |
| Двойное нажатие отправки и сетевой timeout | Один логический запрос с прежним idempotency key; неизвестный итог разрешается через статус, без слепого повтора |
| Истечение session, reauth, logout | Правильные состояния UI, cache очищен, медиа недоступны после logout |
| Ввод и конфликт редактора | Ввод не тормозит, восстановление draft после аварии, конфликт не затирается |
| Upload / thumbnail / album | Прогресс, отмена, ограничение размера, большие файлы без base64/роста памяти; порядок сохранён |
| Пауза очереди / сон / перезапуск | Состояние и расписание сохранены; прежние блокировки отправителя соблюдены |
| Потеря интернета / локального backend | Различимые состояния, ограниченный backoff, черновик сохранён |
| IPC / local API | Отказ неизвестному origin/команде, arbitrary URL/path, повтору bootstrap; user auth не обходится |
| Upgrade / uninstall / reinstall | Backup и сохранение данных; отказ остановки не приводит к принудительному kill |
| Доступность | Клавиатура, Narrator smoke, focus, масштаб, контраст, reduced motion |
| Web/Mini App | Сборка и существующие login/media/навигация работают через WebTransport |

Playwright проверяет frontend в браузерном harness, но не доказывает работоспособность packaged Tauri. Native E2E выполнять через tauri-driver/WebDriver на Windows с подходящим Edge driver; системные диалоги и installer дополнительно проверить вручную/Windows UI automation. Состояние готовности ожидать по признакам интерфейса/сервиса, не по общему networkidle при постоянном polling.

Unit/component-тесты — для гонок поиска, query invalidation, формы/конфликтов, session и состояния редактора. Backend — существующие pytest плюс проверка новых bootstrap/lifecycle/transport границ. Тесты реальной отправки проводить только на выделенном тестовом канале; production-токены и данные не использовать.

## Формат результата каждого этапа

Изменённые модули, выполненные сценарии, команды и результаты проверок, известные ограничения. Для UI — скриншоты состояний; для performance — fixture, версия сборки, машина и сырые измерения. Нельзя писать «готово» по факту компиляции, если нативный запуск или миграция не проверены.

## Поручение ИИ-агенту

Передай следующий текст агенту вместе с репозиторием:

> Реализуй отдельное Windows-приложение Edizora по docs/desktop-app-spec.md и docs/desktop-app-plan.md. Рекомендованные skills и границы их применения перечислены в docs/desktop-app-skills.md. Сначала изучи действующие инструкции репозитория, git status, существующие desktop/frontend/API/auth/host/runtime/installer и тесты. Сохрани чужие изменения. Не трогай рабочие секреты и пользовательские базы.
>
> Стек: Tauri 2 + React 19 + TypeScript strict + Vite, TanStack Query/Virtual, React Router, Radix, CSS Modules. Существующий Python backend сохранить в sidecar. Не переписывай бизнес-логику в Rust и не отключай web/CSRF/authorization ради desktop. Не заменяй работу фиктивными ответами API в production.
>
> Выполняй этапы последовательно: сначала базовая линия и вертикальный прототип с установленной сборкой (login, read, mutation, upload, media, single-instance), затем lifecycle, frontend, функциональный паритет, измерения и installer. При блокере прототипа зафиксируй причину до продолжения. Каждый этап завершай работающим результатом и релевантными проверками, а не только планом следующего этапа.
>
> Сохрани данные, SecretStore, идентичность установки, idempotency, блокировки отправителя, расписания, backup/restore и текущие web/Mini App сценарии. Основное приложение и мастер настройки открываются в собственном окне без браузера; крестик скрывает в трей, явный выход штатно завершает backend. Повторный запуск не создаёт второго отправителя.
>
> Подготовь доступный RU/EN интерфейс со всеми состояниями, адаптацией к масштабу, recovery drafts и защитой от конфликтов. Применяй виртуализацию, lazy routes, адресный query cache и thumbnails. Докажи скорость измерениями по ТЗ, не заявляй её на основании выбора фреймворка.
>
> В результате предоставь исходники, lock-файлы, инструкции сборки, Windows installer с hashes, результаты unit/integration/native E2E и migration-тестов, performance-отчёт и честный список ограничений. Публикацию релиза и операции с production не выполняй без отдельного поручения. Если внешняя среда не позволяет проверить критерий, явно обозначь его непроверенным.

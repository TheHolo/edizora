# Установка, резервные копии и перенос веб-версии

Реализация подготовлена на изолированной копии дерева, включая исходные незакоммиченные файлы. Рабочие токены, рабочая SQLite и публикационные каналы для этих проверок не использовались.

## Что реализовано

`app/host/control.py` хранит идентичность узла, поколение, независимые причины остановки, допуски начатых отправок и управляющий журнал вне переносимой SQLite. Отсутствующая идентичность означает `recovery_required`. Копирование SQLite не создаёт владельца. Tombstone `retired.json` запрещает обычный повторный запуск источника; новый перенос обратно может заменить его только подтверждённым новым поколением.

`app/deployment/controller.py` выполняет проверку плана и готовности очереди, общую остановку через реальные runtime hooks, отзыв старых AI lease, SQLite Backup API, SHA-256/семантическую сверку и передачу права. Решение о передаче фиксируется до обращения к target. Потерянный ACK оставляет источник остановленным и требует сверки того же разрешения; автоматического отката после commit нет. Target сохраняет migration gate до проверки маршрута и финального checkpoint. Источник хранит собственный журнал, а target получает итоговый отчёт и квитанции.

`app/deployment/snapshot.py` проверяет целостность SQLite и foreign keys, сохраняет все таблицы/ID/JSON, относительные файлы и их хеши. Ненулевой WAL входит в согласованный снимок через Backup API. Абсолютные пути, `..`, UNC/drive, symlink, конфликт регистра и zip-slip отклоняются. Передача в staging проверяется до подмены рабочего набора. Существующий набор target архивируется отдельным каталогом, без построчного слияния. Возврат переносит актуальный снимок нынешнего владельца.

`app/host/secrets.py` хранит значения в AES-GCM. На Windows ключ защищён DPAPI текущего пользователя, на Linux — приватным ключевым файлом внутри каталога 0700. Для переноса разрешённые секреты дополнительно шифруются X25519/HKDF/AES-GCM для публичного ключа target и связаны с system/node/migration/generation. В резервной копии используется отдельный пароль восстановления, scrypt и AES-GCM. Пароли восстановления не пишутся в журнал. Секреты домашнего AI остаются дома.

`app/deployment/paramiko_transport.py` выполняет SSH-вход по ключу/паролю, введённому в интерфейсе. Доступ хранится только в памяти controller. Приватный ключ открывается из памяти без временного файла, `RejectPolicy` и закреплённый `known_hosts` обязательны. До остановки выполняется только чтение ОС/архитектуры/места/идентичности и проверка необходимых sudo-прав. После подтверждённого gate/drain передаётся тот же проверенный релиз и запускается фиксированный комплектный Ubuntu-установщик в пассивной роли. После установки отдельно проверяются фактические node/release/schema. Пароль, ключ и сырой вывод удалённой команды не попадают в progress или SQLite контента.

`app/deployment/ssh.py` сохраняет путь для заранее настроенного OpenSSH с `BatchMode=yes`, `StrictHostKeyChecking=yes` и явно подтверждённым `known_hosts`. Удалённые действия ограничены командами `publisher-node-agent`; произвольная команда из веб-формы не выполняется. `app/deployment/pull.py` позволяет Windows host за NAT получать команды и нынешний облачный snapshot исходящими SSH-соединениями. Домашний входящий публичный порт не нужен.

Это реализация протокола и транспорта; испытание трёх направлений на реальных Ubuntu/Windows машинах остаётся отдельным внешним этапом. Локальные файловые fixtures не объявляются настоящей миграцией ОС или SSH.

## Подготовка релиза

После сборки frontend и приёмочных проверок:

```powershell
.\.venv\Scripts\python.exe -m app.deployment.cli build-release --source . --output .\release
```

Команда берёт реальные проверенные файлы рабочего дерева, а не старый Git HEAD. ZIP содержит backend, исходники и сборку frontend, lock-файлы, миграции, установщики, тесты и документацию. `.env`, рабочие данные, `.venv`, `node_modules`, кэши и Git не входят. Время/права ZIP нормализованы; повтор одной и той же сборки даёт тот же SHA-256. Manifest перечисляет размер и SHA-256 каждого файла; ID релиза определяется содержимым.

Полученный SHA-256 передаётся установщику по доверенному каналу. Контрольная сумма сама по себе не доказывает доверенность скачанного архива.

## Windows

Нужны Python 3.12 с launcher `py`, PowerShell и OpenSSH client. Установка принимает проверенный ZIP, его SHA-256 и UUID существующей системы:

```powershell
powershell -File deploy\install-web-windows.ps1 -ReleaseArchive <release.zip> -ExpectedSha256 <sha256> -SystemId <system-uuid>
```

По умолчанию программа, данные и control state разделены внутри `%LOCALAPPDATA%\Edizora`. OneDrive и UNC не подходят для активной SQLite. Существующая рабочая БД не перемещается этой командой. Повтор того же релиза проверяет уже установленные файлы; смена релиза требует отдельного остановленного обновления.

Host устанавливается пассивно. Для первой новой пустой установки доверенная локальная настройка выполняется с `app.web --initialize --activate-initial-installation --admin-id ... --set-password --setup-only` при заданных путях control/data/database установленного host. Флаг активации допускается только для пустого standby первого поколения без истории переноса, tombstone и причин остановки; удерживается штатный host.lock. Обычный `--initialize` не меняет роль standby. Для назначения миграции первоначальную настройку не запускать: сохранить standby и отсутствующую БД до подтверждённой передачи. Копия существующей БД не может получить право запуска через первоначальную активацию.

Управление установленным host:

```powershell
powershell -File "$env:LOCALAPPDATA\Edizora\manage.ps1" -Action Start
powershell -File "$env:LOCALAPPDATA\Edizora\manage.ps1" -Action Stop
powershell -File "$env:LOCALAPPDATA\Edizora\manage.ps1" -Action Restart
powershell -File "$env:LOCALAPPDATA\Edizora\manage.ps1" -Action InstallAutostart
powershell -File "$env:LOCALAPPDATA\Edizora\manage.ps1" -Action RemoveAutostart
```

Автозапуск создаётся только явной командой и под текущим пользователем. Остановка проходит через host, а не принудительное завершение отправителя. Старые ярлыки/службы/контейнеры прежнего неуправляемого бота нужно выявить и отключить перед первым промышленным включением.

Штатный Windows launcher включает Telegram polling и публикатор параметром `--enable-bot`; роль standby и migration/recovery gate продолжают запрещать их запуск до подтверждённой активации. Для локальной проверки интерфейса без внешних отправок используйте отдельный тестовый профиль и прямой `app.web` без `--enable-bot`.

## Ubuntu 24.04 LTS x86-64

Поддерживаемый первый профиль именно Ubuntu 24.04 LTS x86-64. Это не утверждение, что он является последней LTS. Сроки поддержки сверяются с [официальным циклом Ubuntu](https://ubuntu.com/about/release-cycle).

```sh
sudo bash deploy/install-web-ubuntu.sh /path/release.zip EXPECTED_SHA256 SYSTEM_UUID publisher.example.org
```

Установщик проверяет ОС/архитектуру, release manifest и хеши, создаёт непривилегированного пользователя `publisher`, отдельный venv для релиза и systemd unit. Данные: `/var/lib/publisher/data`; control/secrets: `/var/lib/publisher/control`; конфигурация: `/etc/publisher/host.env`; программа: `/opt/publisher/releases/<release-id>`. Состояние назначения — standby. Боевые файлы источника не копируются и право публикации не выдаётся.

При указанном домене готовится отдельный `/etc/caddy/publisher.caddy`. На чистой машине создаётся выделенная служба `publisher-proxy`, а только что установленная стандартная служба Caddy отключается, чтобы не занять те же порты. Чужой уже существующий Caddyfile/служба не перезаписывается: в этом случае добавить `import /etc/caddy/publisher.caddy` в управляемую конфигурацию, проверить `caddy validate` и выполнить reload. DNS/сертификат и публичный путь проверяются реальным HTTPS challenge целевого узла; мастер остаётся на routing до подтверждения. Шаблон использует [официальный reverse_proxy Caddy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).

```sh
sudo systemctl enable --now publisher-host
sudo systemctl status publisher-host
sudo journalctl -u publisher-host -n 100
```

Зависимости устанавливаются из `uv.lock` с `--frozen`; bootstrap `uv` закреплён на использованной при сборке линии. Семантика frozen описана в [официальной документации uv](https://docs.astral.sh/uv/concepts/projects/sync/). Установщик не запускает произвольный скрипт `latest`, не закрывает SSH/firewall и не переключает прежний активный релиз автоматически.

## Доверенная SSH-привязка

Для обычного мастера:

1. Источник должен быть установлен из проверенного релиза. Установщики сохраняют его ZIP и запись `installed-release/current`; перенос не собирает произвольный новый код вместо установленной версии.
2. Создать профиль в интерфейсе (host/user/port/HTTPS). Ввести SSH-пароль либо приватный ключ и при необходимости пароль ключа и sudo. Пароль панели провайдера не является SSH-паролем. Поля не сохраняются в браузерном хранилище, а controller держит их только до своего перезапуска.
3. Запросить fingerprint, сверить его по независимому доверенному каналу и явно подтвердить выбранный ключ. Сканирование само по себе не делает сервер доверенным. Изменившийся уже закреплённый ключ блокирует соединение.
4. Пройти настоящую проверку Ubuntu 24.04 x86-64, диска, sudo и отсутствия чужих данных/служб. Отсутствие агента на чистом VPS не мешает построить план: показано «будет установлен». После start мастер сначала останавливает источник, затем устанавливает ровно тот же release в standby и проверяет его идентичность.
5. При перезапуске controller повторно ввести SSH-доступ. Gate и checkpoints остаются на месте. «Продолжить» не меняет target или зафиксированное разрешение.

Альтернативный путь для уже установленного пассивного target и настроенного OpenSSH:

```sh
python -m app.deployment.cli --control-dir <control> register-ssh <profile-id> --known-hosts <known_hosts> --identity-file <private-key>
```

В этом CLI-варианте пути ключа и known_hosts остаются в приватном control state, не в контентной БД. Веб-форма не получает возможность подставлять произвольные локальные файлы. Ключ или SSH agent должен принадлежать пользователю службы. На Ubuntu команда `publisher-node-agent` устанавливается в `/usr/local/bin`; при необходимости транспорт выполняет её как непривилегированный `publisher`, а sudo используется только для фиксированной установки/службы. Проверка действительных прав и host keys входит во внешнюю приёмку. Публичные API и команды ограничены; это соответствует [политикам SSH-клиента Paramiko](https://docs.paramiko.org/en/stable/api/client.html).

Для возврата облака домой Windows host в пассивной/retired роли запускает исходящий bridge:

```powershell
python -m app.deployment.cli --control-dir <home-control> bridge --host <active-cloud-host> --user publisher --known-hosts <known_hosts> --identity-file <key>
```

Bridge регистрирует свой node ID/system ID, опрашивает облачный controller и загружает именно его новый snapshot. После выключения ПК план не выдаёт готовое назначение; операция ожидает живой host. Bridge должен продолжать работать до финальной квитанции. Старый локальный набор архивируется при активации, не объединяется с облачным.

## Резервные копии и восстановление

Ручная полная копия использует реальную остановку writers и отправок. Если в установке есть переносимые секреты, нужен отдельный пароль восстановления не короче 12 символов. Сохраните его отдельно от машины и резервной копии. Без этого пароля ключи DPAPI старого пользователя/компьютера не заменят восстановление на другой ОС.

Расписание по умолчанию выключено. После явного включения начальный профиль — раз в 24 часа, сохранить 7 проверенных копий. По желанию ключ расписания сохраняется только в машинном защищённом хранилище. Retention удаляет только избыточные проверенные UUID-каталоги внутри backup root, оставляя как минимум последнюю пригодную копию. Некорректные/неполные снимки сохраняются для разбора.

Restore сначала проверяет пакет, систему/релиз/схему/хеши и пароль на временных данных. До замены создаётся отдельная копия текущего состояния. Работа исполняется серверной фоновой операцией и переживает закрытие вкладки. После замены действует независимый `recovery` gate: публикации не начинаются сами. Явное завершение восстановления переводит восстановленную ожидающую очередь в черновики для проверки возможных повторов; исходное расписание/порядок сохраняются в `post_data.restore_review`, а переход — в журнале. Повторная постановка каждого материала требует обычного осознанного действия владельца.

После перезапуска незавершённая операция не остаётся вечной running: host вызывает `recover_pending()`. Пауза сохраняется; разрешены только безопасные действия соответствующего этапа. После committed handoff обычного «вернуть источник» нет.

## Реальная внешняя приёмка перед эксплуатацией

Локальные автоматические проверки используют временные SQLite, файловые target и подставленные runtime hooks; отдельная интеграционная проверка host запускает настоящие процессы runtime. Они доказывают программные инварианты на данном Windows-стенде, а не работу конкретного VPS, systemd, Caddy, SSH-прав или Telegram-клиента.

Для завершения внешней приёмки подготовить: чистую Windows установку, два Ubuntu 24.04 LTS x86-64 узла, управляемый HTTPS-домен, служебные SSH-ключи с подтверждёнными fingerprints и разрешённый тестовый Telegram-канал. Рабочие токены в испытаниях не использовать.

Последовательность:

1. Установить одинаковый проверенный релиз; записать release/schema/system/node IDs, OS/arch и SHA-256. Повторить установщик без изменения файлов/данных. Проверить штатный restart и отказ старого запуска после retirement.
2. Создать изолированные черновики/очередь/историю, кириллические имена медиа, файл из WAL, точные даты, user pause и неопределённую попытку. Проверить контрольный отчёт.
3. Windows → Ubuntu: начать во время удержанной отправки; новый permit запрещён, прежняя сессия завершается, quiesced только после фактического drain. Закрыть вкладку. Сверить snapshot/media/ID/message IDs/очередь на target; источник retired после reboot.
4. В облаке добавить новые правки и тестовую подтверждённую публикацию. Ubuntu → Windows за NAT: получить именно новую облачную БД; новая публикация не повторяется, старый домашний набор архивирован.
5. Ubuntu → Ubuntu с выключенным домашним ПК: прямой SSH transfer, закрытая вкладка, журнал и последующий перенос доступны новому владельцу.
6. Оборвать сеть до/после всех checkpoint, особенно после принятия target activation до ACK. Источник не оживает; повтор resolve получает прежнюю квитанцию. Повредить байт медиа/БД, заполнить диск, изменить SSH host key и snapshot/node/generation в разрешении: активация запрещена.
7. Проверить HTTPS challenge с публичного маршрута, DNS-кэш старого origin, Mini App и worker endpoint. До routing/final checkpoint target владеет данными, но migration gate ещё закрыт.
8. Создать полную backup с шифрованными секретами, проверить неверный пароль и восстановить на временной установке. Убедиться в recovery gate, сохранении старого набора и ручной проверке очереди.

Результаты фиксируются отдельно для каждого направления и клиента. До выполнения этого сценария реальные SSH-переносы, чистые ОС-установки и сетевые условия считаются непроверенными.

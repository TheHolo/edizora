# Desktop Edizora: прототип и проверка

Состояние: вертикальный прототип этапа 1 проверен; жизненный цикл этапа 2 реализован частично и проверяется, начаты общий транспорт и query cache этапа 3. Это **не готовый выпуск** и не замена действующего установщика. Прототип запускается только с явно указанным изолированным каталогом, содержащим маркер `.edizora-prototype`; рабочие профили и данные не использовались.

## Базовая линия

До миграции `npm run build` и `npm run test:client` проходили: 13 клиентских тестов; JS основной страницы — 136,19 KiB gzip. Прямой прогон pytest в этой среде сначала столкнулся с недоступным системным временным каталогом. Запуск с `--basetemp` внутри проекта дал 679 пройденных, 2 пропущенных и ошибки создания 10 legacy-fixture. При размещении legacy-fixture в OneDrive три проверки ожидаемо отвергли эту папку как небезопасную для SQLite; все 10 проверок `tests/test_web_legacy_import.py` прошли при размещении фикстур вне OneDrive.

Повторный полный прогон с отдельной временной папкой вне OneDrive: 699 пройденных, 2 пропущенных. ## Что реализовано в прототипе

- Отдельный headless launcher использует первый запуск и существующий host/runtime, не открывает браузер и не запускает Python-трей. Порты host и runtime закрепляются bind на `127.0.0.1:0` до передачи адреса; runtime получает уже открытый сокет.
- Nonce и транспортный credential передаются через stdin; повторное подключение к уже занятому host требует проверки HMAC challenge, установочной identity и защищённого Windows DPAPI ключа. Авторизация пользователя и CSRF остаются обязательными.
- Экспериментальный Tauri bridge ограничивает методы и пути OpenAPI, держит cookie и CSRF в памяти, использует native file picker с непрозрачным handle и отдельный медиапротокол. Загрузка в runtime передаётся бинарным потоком, не base64 внутри RPC.
- UI прототипа предназначен только для проверки нескольких операций. Полный существующий UI пока не перенесён. Старые web/Mini App маршруты и старый установщик остаются действующими.
- `deploy/build-desktop-prototype.ps1` собирает **отдельный** тестовый установщик в новом подкаталоге `output/desktop-prototype/`; он не регистрирует установленный продукт и не создаёт ярлыки. `desktop-tests/prototype_native.py` принимает только новый каталог тестового профиля и создаёт синтетическое изображение.
- Этап 2: добавлены трей и штатное завершение, проверка идентичности host перед остановкой и ожидание освобождения блокировок setup/host/runtime. Мастер сначала синхронизирует завершение с выполняющейся настройкой и отклоняет поздние запросы. Если host аварийно исчезает, исполнитель получает EOF по унаследованному каналу и штатно ожидает завершения операций; автоматический повтор отправки с неизвестным результатом по-прежнему запрещён. В оболочке добавлены ограниченные повторные попытки и проверка HMAC подключённого host. Подготовлена проверка пути будущего автозапуска к соседней установленной оболочке; запись проверялась на подменённом реестре. Изолированная сборка ни читает, ни меняет системный автозапуск.
- Оболочка сообщает интерфейсу о скрытии, сворачивании и восстановлении окна. Это необходимо отдельно от `document.hidden`: WebView2 может считать скрытое нативное окно видимым. В установленной и отладочной сборках на реальном окне проверены остановка периодического опроса при скрытии и сворачивании, фоновый запуск и возобновление одного опроса после повторного запуска.
- Выделен общий транспорт: web сохраняет same-origin cookies, CSRF и bearer Mini App, а desktop передаёт JSON ограниченному Rust bridge без передачи ему браузерных credentials. Для неизвестного результата сохраняется ключ операции, включая случай конкурирующих запросов; идентичность операции изолирована по пользователю и хранится как digest. Отмена ожидания JSON-запроса в desktop пока не отменяет уже переданный bridge запрос. Desktop-вариант медиа выдаёт непрозрачные ссылки с отзывом, а файловый диалог возвращает ограниченные handles для потоковой загрузки.
- Существующие web-экраны используют общий TanStack Query cache: запросы адресуются по пользователю и пути, одинаковые чтения объединяются, устаревший поиск отменяется, при logout и смене пользователя данные и выбранный канал очищаются. Автоматический повтор mutations выключен. Проверка Playwright на изолированном браузерном профиле с синтетическим API покрывает вход, повторное использование списка каналов, logout с CSRF и смену пользователя. Desktop-прототип использует общий JSON-клиент, но полноценный общий интерфейс и привязка native visibility к Query ещё не перенесены.
- Маршруты переведены на React Router: для web сохранены обычные адреса, для будущего desktop-интерфейса подготовлена hash-история. Браузерная проверка подтвердила сохранение ввода при отмене перехода по ссылке и кнопкой «Назад», загрузку synthetic multipart-файла с CSRF и отображение thumbnail. Hash-режим пока не проверен внутри полноценного desktop-интерфейса.

## Повторение проверки

Нужны Windows 11 x64, WebView2, Node/npm, Rust, Python-окружение проекта и Inno Setup. После установки зависимостей проекта прототип собирается командой `./deploy/build-desktop-prototype.ps1`; при другом пути к компилятору Inno используется параметр `-Compiler`. Сборка выводит каталог установщика и SHA-256. Это неподписанный тестовый установщик, не установщик выпуска.

Устанавливать его следует только в отдельный каталог. При запуске требуется переменная `EDIZORA_PROTOTYPE_ROOT` с абсолютным путём к отдельной тестовой папке, содержащей файл `.edizora-prototype`. Нельзя добавлять этот маркер в рабочую установку. Не используйте прототип с рабочими данными.

Для native smoke `desktop-tests/prototype_native.py` нужны `PUBLISHER_TEST_APPLICATION` (путь к установленному exe), `PUBLISHER_TEST_EDGE_DRIVER`, `PUBLISHER_TEST_TAURI_DRIVER` и `PUBLISHER_NATIVE_FIXTURE` (новая абсолютная папка). Скрипт выводит путь к синтетической картинке, которую необходимо выбрать в системном диалоге; после этого сценарий проверяет отзыв медиа и штатно останавливает тестовый host.

При `PUBLISHER_NATIVE_TRAY_CLICK=1` тот же тест дополнительно ожидает два системных закрытия окна, проверяет объяснение и скрытие в трей, повторный запуск и штатное завершение. При `PUBLISHER_NATIVE_EXIT_DURING_SETUP=before` или `1` он проверяет выход до настройки или одновременно с её запуском. `desktop-tests/recovery_native.py` создаёт новый профиль, ставит публикации на паузу и на нём проверяет аварии shell и host; перед завершением тестового процесса он сверяет его путь с установленным прототипом и проверяет отсутствие токена и отправок.

Параметры `PUBLISHER_CHECK_HIDDEN=1` и `PUBLISHER_CHECK_BACKGROUND_POLL=1` добавляют проверку при скрытии и фоновом запуске. При `PUBLISHER_CHECK_MINIMIZED=1` тест выводит `MINIMIZE_READY` и ожидает сворачивания своего окна средствами Windows, после чего проверяет отсутствие таймера опроса и восстановление при обычном повторном запуске.

При `PUBLISHER_NATIVE_MULTI_PICKER=1` тест создаёт два синтетических изображения, проверяет отказ выбора до входа, ожидает их выбора в системном диалоге и проверяет streaming upload и отзыв неиспользованного handle. Сценарий прошёл в отладочной оболочке с backend установленного прототипа; установщик `903d` собран до этой доработки.

`desktop-tests/background_native.py` проверяет фоновый запуск на заранее созданном performance-наборе и параллельно создаёт второй пустой тестовый профиль. Для `desktop-tests/setup_modes_native.py` задаётся `PUBLISHER_SETUP_MODE=legacy` или `restore`: скрипт создаёт синтетический источник и проверяет его сохранность после настройки. Все эти сценарии требуют явно указанных путей к тестовому исполняемому файлу и тестовым каталогам; они не предназначены для рабочих установок.

`desktop-tests/startup_delay_native.py` использует отдельно собранную заглушку `fake_slow_backend.rs`, которая не открывает сеть или базу. Тест проверяет предупреждение через 30 секунд, отсутствие второго процесса при повторной проверке, повторный запуск после завершения первого и безопасный выход. Сборочный скрипт выполняет Python-этапы из отдельного временного каталога, чтобы не загружать `.env` и настройки checkout как текущего каталога.

Проверка web-интерфейса: в каталоге `frontend` выполнить `npm run build`, затем указать `PLAYWRIGHT_BROWSER_EXECUTABLE` с путём к установленному Chromium-совместимому браузеру и запустить `npm run test:web`. Тест создаёт отдельный браузерный профиль, отдаёт только синтетические ответы и блокирует остальные сетевые запросы. `npm run test:client` проверяет транспорт, изоляцию и отмену запросов без браузера.

`desktop-tests/generate_performance_fixture.py` создаёт изолированный набор; `desktop-tests/measure_prototype.py --help` описывает замеры дерева процессов и опциональное окно измерения CPU. `desktop-tests/measure_native_startup.py` сохраняет измерения видимой формы после каждого запуска и может продолжить серию с `--resume`. `desktop-tests/benchmark_preparations.py` позволяет отдельно сравнить исторический и текущий обход черновиков; оба инструмента отказываются работать без маркера тестового набора и проверяют отсутствие токена бота и паузу публикаций.

На подготовленном наборе с 8 021 ожидающим подтверждения черновиком отдельный прогон исторического обхода занял около 646 мс и выделил до 54,7 MiB по `tracemalloc`. Текущий фильтр и постраничный обход заняли около 76 мс и выделили до 1,8 MiB. Это микрозамеры Python-выделений, не память всего приложения и не p95; при изменении базы полный проход по-прежнему проверяет версии и отпечатки каналов перед созданием операций.

## Незакрытые критерии

В установленном WebView были проверены мастер, настройка, вход, чтение, изменение тестового канала, системный выбор файла, бинарный upload, защищённое медиа, logout и повторный запуск. Проверка прошла как для debug-оболочки, помещённой в каталог установленного прототипа, так и для установленных release-сборок. Сборка `7b3d2819cb794bbc850438b286ccb6f3` дополнительно прошла сценарий через экранные формы; [скриншоты](desktop-prototype-screenshots/) показывают мастер, вход, рабочую область и синтетическое изображение. Первые попытки выявили несовместимость вербатим-пути Windows с SQLite и кэширование изображения WebView после logout. Исправления проверены повторным нативным запуском: путь нормализуется, а после очистки сессии документ WebView перезагружается и старый адрес медиа недоступен.

Тестовый установщик `4d1d5fb2da3f4400aeb4e6217578e9ea` (SHA-256 `7437ac982a159380754430266cafe94d61950868df4f7180da1cdd8a9f88f910`) установлен в отдельный каталог. Он прошёл сценарии закрытия до и во время первой настройки, а также входа, файла, logout, первого и повторного закрытия в трей, повторного открытия и явного завершения с освобождением блокировок. Скриншот сообщения при первом закрытии сохранён в том же каталоге.

Более новая установленная сборка `6654cca599ec4ad9a42c447df5666976`, SHA-256 установщика `b18305b6fc0bc048b74e2e00c79aa6a12f10fae0b04418e0d294510426fcafc4`, повторно прошла эти проверки и отдельный тест аварий: после принудительного завершения тестовой оболочки новый экземпляр подключился к тому же host и runtime; после аварий подключённого и собственного host runtime штатно освободил блокировку, новый host восстановился, сессия была очищена, а тестовый канал сохранился. Очередь была на паузе, действующих отправок и Telegram-токена не было. Проверка не моделирует обрыв в середине реальной отправки и не является приёмкой выпуска.

В установленной сборке `39080bb6acd748e38f1b70d7f4e5346b`, SHA-256 установщика `c4b4ebc20738ff7a97fe6bdd57c9497c68474d06f9645a04513cf7206c65d2ca`, повторно прошли форма, системный выбор файла, logout, закрытие окна, повторный запуск, штатное завершение и гонка выхода с настройкой. Проверены две одновременные тестовые установки: у каждой отдельный экземпляр, повторный фоновый запуск не создаёт второй host, а первый мастер остаётся видимым. Native-тесты импорта legacy и восстановления backup проверили исходную SQLite и manifest, сохранение идентичности и паузу очереди; незавершённая legacy-отправка помечена как требующая сверки.

Установленная сборка `90ae87113a044246bb825468e2260647`, SHA-256 установщика `2553adbb289b405fa032b56630bcf78a5fe8ba6f148974c9ed957836578a19c8`, дополнительно прошла тест медленного запуска с заглушкой. Предыдущая сборка в контрольном прогоне не показывала объяснение ожидания; новая не создаёт второй процесс и выполняет безопасное завершение во время повторного запуска. Исполняемый файл, взятый из установленного каталога для теста, совпал по SHA-256 с payload установщика.

Установленная сборка `903d6559f2c24d319eaf297dd0670cad`, SHA-256 установщика `3891db846b492a594a3c76c055f81e9ab5d597f3105e2d289d4d31bb42ed9806`, дополнительно прошла сценарии скрытого, свёрнутого и фонового окна. После повторного запуска проверены восстановление окна и возобновление опроса. Тест также выполнил настройку, вход, чтение, тестовое изменение, загрузку синтетического изображения, отзыв медиа при выходе и завершение с освобождением блокировок. Хеш установленной оболочки совпал с payload. Этот установщик собран до начатого ниже выделения общего транспорта.

Последующий отладочный payload с общим JSON-клиентом прошёл нативный сценарий настройки, входа, создания канала, медиа, logout и штатного завершения. В дополнительном сценарии реальные диалоги Windows вернули два синтетических файла: один передан потоком, второй отозван и больше не принимается bridge. Клиентские проверки — 25/25, Rust unit — 7/7; проверка web в Playwright выполнена на синтетическом API. Данные рабочего приложения не использовались.

Сборка `3908` сохраняет положение и размер окна в тестовом профиле, переносит окно с недоступными координатами на доступный экран и очищает видимую рабочую область при потере backend. Тест искусственно задал координаты отсутствующего экрана, переместил окно средствами Windows, перезапустил оболочку и повторил сценарии аварий. Фактическое отключение монитора не проверялось.

Предварительный замер release-сборки до оптимизации на Windows 11 (32 логических процессора, профиль с 10 000 публикаций, без Telegram-токена и AI) дал 6 603 мс до готовности host и 632,0 MiB private bytes всего дерева процессов через одну секунду. Это один пробный замер, а не p95 и не приёмка: целевые 3 секунды тёплого запуска и 350 MiB не подтверждены. Профилирование выявило преждевременный импорт Telegram и модулей AI в двух Python-процессах; после переноса импортов на момент использования три пробных запуска дали 4 305–4 370 мс и 359,8–373,0 MiB. После оптимизации прохода по готовым черновикам в дополнительном минутном пробном замере получено 362,2 MiB в конце окна и 14,51% одного ядра; параллельно на машине шли сборка и тесты. Повторный проход без изменений базы устранён через наблюдение SQLite `data_version`. В установленной сборке следующий минутный пробный замер дал 344,4 MiB к концу окна и выборочный максимум 345,9 MiB; средний CPU составил 9,64% одного логического ядра, или 0,30% мощности этой 32-поточной машины. Измерение проводилось на экране до входа и не заменяет приёмку на эталонном компьютере. Сырые данные и состав процессов: `docs/desktop-prototype-measurements.json`. Готовность host в этом запуске составила 4 393 мс. Прототип не содержит проверенный production lifecycle, полноценные общие desktop-экраны, восстановление черновиков, окончательный Inno installer или полный performance-отчёт. Системный автозапуск в изолированной сборке намеренно выключен. Если начальный запуск завис и его завершение не подтверждено, повторная проверка сообщает об ожидании, но не создаёт ещё один backend; автоматическое восстановление такого зависания пока не реализовано. Непосредственный клик по значку и меню трея пока не проверен: область уведомлений недоступна через имеющуюся автоматизацию. Не выполнены проверки upgrade/uninstall на чистой Windows VM, Windows shutdown/sleep, восстановления окна после физического отключения монитора и полной доступности; большой набор использован только в указанных пробных замерах. При завершении сеанса Windows штатный drain пока не подтверждён: используемая оконная библиотека завершает процесс при системном `WM_ENDSESSION`. Это ограничение необходимо устранить и проверить до выпуска. Артефакт не подписан.

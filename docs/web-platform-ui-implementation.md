# Веб-панель: реализация и проверка

Дата: 26 октября 2026. Исходники: frontend/. Этот отчёт описывает клиентскую часть; состояние backend, миграций и внешних испытаний фиксируется в общем журнале исполнения.

## Поставка

Одна русская React/TypeScript-панель для обычного браузера и Telegram Mini App. Production-сборка находится в frontend/dist/ и работает с реальным API того же origin /api/v1. Демонстрационных записей, имитации прогресса и автопубликации при открытии страницы в клиенте нет. Node.js нужен для разработки и сборки, но не для запуска готовой панели.

Версии закреплены в package.json и package-lock.json: React 19.1.1, TypeScript 5.9.3, Vite 7.3.7, openapi-typescript 7.13.0. Vite обновлён после фактического npm audit; выбран исправленный выпуск той же основной линии. Проверен [официальный выпуск Vite 7.3.7](https://github.com/vitejs/vite/releases/tag/v7.3.7).

## Клиентская безопасность и Mini App

Сессия браузера использует cookie и CSRF-заголовок. Mini App bearer живёт только в памяти. В sessionStorage находятся только несекретные exchange nonce и время короткого окна обмена. Bearer, initData, SSH-доступ и пароли не записываются в localStorage/sessionStorage или URL. Из URL удаляется локальный одноразовый код до дальнейшей работы.

Ключ принятой команды сохраняется в памяти при потере HTTP-ответа и используется повторно для той же команды. Клиент не повторяет опасный POST автоматически с новым ключом. У кнопок есть блокировка на время принятия. Медиа для bearer-сессии загружаются с авторизацией только с origin приложения, с отложенной загрузкой и освобождением blob URL.

Telegram-интеграция включает ready/expand, тёмные цвета, BackButton, изменение viewport/safe areas, предупреждение при несохранённом вводе, открытие внешних ссылок через поддерживаемый SDK. Это реализация интеграции, а не доказательство её работы во всех клиентах Telegram.

## Проверки

Из каталога frontend/:

    npm ci
    npm run gen:api
    npm run check
    npm run test:client
    npm run build
    npm audit --json

Перед генерацией backend экспортирует актуальный docs/openapi.json командой python -m app.api.export_schema. Файл src/generated/api.ts создаётся закреплённым openapi-typescript. Канонические поля Publication/Channel/Operation и вложенные Album/Readiness/Schedule используются клиентскими типами. Проверка check:api сравнивает сгенерированный файл с текущей схемой; check и build завершаются ошибкой при рассогласовании.

На Node 24.11.0/npm 11.6.1:

- npm run check: успешно.
- npm run test:client: 7 из 7. Потеря ответа/повтор ключа, разные payload, CSRF/bearer, GET/204, fresh reauth без автоповтора, запрет передачи bearer внешнему media origin, нормализация фактических DTO.
- npm run build: успешно. Готовая сборка примерно 320 КБ JS и 41 КБ CSS до gzip.
- npm audit --json: 0 уязвимостей во всех зависимостях, включая dev, после закрепления Vite 7.3.7.
- Расчёт контраста: основной текст/фон 14,60:1; вторичный текст/поверхность 7,62:1; текст основной кнопки/мятная заливка 8,50:1; placeholder/поле 5,95:1. Граница поля усилена до #5D707D, контраст с полем 3,38:1.

Node-тесты API-клиента используют только искусственные HTTP-ответы и не заменяют интеграционные испытания. Реальные браузерные снимки и проверки сохранения/перезагрузки проводятся отдельно основным исполнителем на изолированном backend и входят в общий отчёт.

## Необходимые внешние испытания

Не считать автоматически пройденными: Telegram Android, iOS и Desktop; реальная экранная клавиатура и системные safe areas; реальный SSH fingerprint, права sudo, сетевой обрыв и смена узлов; внешний HTTPS и открытие Mini App из меню бота.

Для каждого Telegram-клиента: открыть кнопку панели по HTTPS → пройти initData-вход → проверить все разделы через «Ещё» → изменить поле → проверить BackButton и предупреждение → сохранить → открыть долгую операцию → закрыть/переоткрыть Mini App → убедиться в сохранении того же operation ID. Отдельно проверить экранную клавиатуру и доступность последнего поля/действия.

Для SSH: создать профиль → передать тестовый ключ в память controller → получить fingerprint → сверить его с доверенной консолью → подтвердить → проверить ОС/диск/роль → составить план без остановки → запустить перенос только в согласованном тестовом окружении. После перезапуска controller несохранённый SSH-доступ вводится заново; отсутствие доступа не разрешает самовольный rollback.

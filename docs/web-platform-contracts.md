# Контракты приложения Publisher

Приложение к [ТЗ](web-platform-spec.md), версия 1.0 от 25 октября 2026 года. Имена маршрутов и полей ниже — базовый контракт; уточнения фиксировать в OpenAPI и одновременно в документации/тестах. Семантику нельзя менять только для удобства фронтенда.

## 1. Постоянные данные

### 1.1. Совместимость существующих таблиц

Сохранить `users`, `channels`, `channel_member_snapshots`, `jobs`, `news_tasks`, `media_items`, `publications`, `job_events`, их первичные ключи и связи. Не пересоздавать задания из ссылок и не перенумеровывать их. Добавить Alembic либо эквивалентный последовательный журнал миграций; предпочтителен Alembic с SQLite batch migration там, где необходима перестройка таблицы.

Начальная миграция распознаёт фактические варианты прежней additive-схемы, проверяет колонки/индексы и только затем отмечает baseline. Нельзя слепо поставить stamp на неизвестную БД. Миграции запускает один управляющий процесс при остановленных исполнителях; не каждый HTTP worker при старте. Сбой не оставляет приложение работающим на половине новой схемы.

`Job.version` и `Channel.version` — целые монотонные версии, исходное значение 1. Любая значимая правка из UI, Telegram или AI увеличивает соответствующую версию. `updated_at` остаётся временем, но не единственной защитой от гонок. JSON исходника получает `schema_version`; чтение прежних записей поддерживается без молчаливого уничтожения неизвестных полей.

`NewsTask.origin_chat_id` становится nullable. Создание из веба не требует фиктивного Telegram-чата. Существующий внутренний User продолжает связываться с разрешённым Telegram ID; создавать новую таблицу организаций/тенантов не нужно.

### 1.2. Необходимые новые сущности

Допускается физически объединять близкие сущности, сохраняя описанные ограничения и проверяемость.

| Сущность | Обязательные данные / ограничения |
| --- | --- |
| ApplicationState | system ID; версия настроек; независимые publication blocks (`user_pause`, `migration`, `recovery`) с owner operation ID; maintenance state; политика просрочки; дата изменения. Gate закрыт при любой действующей причине. Это не единственное доказательство права узла на запуск. |
| QueueRevision | channel ID; revision. Увеличивается при постановке, снятии, claim, смене порядка/времени и иных изменениях состава/семантики очереди. |
| Operation | UUID/public ID; kind; actor; связанные Job/AI-task; status; stage; version; timestamps; измеримый прогресс; структурированная ошибка; result refs; cancel flag. |
| OperationEvent | operation ID; монотонный sequence; stage/status; безопасное сообщение; время; прогресс. Не содержит секреты или полный произвольный traceback. |
| MediaAsset | UUID; source kind/reference; относительный storage key; SHA-256; MIME/размер/размеры кадра; state; thumbnail key; Telegram file ID при наличии; created/accessed timestamps. |
| JobAsset | job ID; asset ID; source index; selected/order; назначение. Для исходников без локального файла допустим source reference и состояние unavailable/remote. |
| CommandReceipt | principal ID; scope/route; idempotency key; canonical payload hash; результат/operation ID; создано/завершено. Уникальность тройки principal/scope/key. |
| TelegramInbox | bot ID; update ID; payload; время приёма/обработки; состояние; связь с результатом. Уникальность bot ID/update ID. |
| PublicationAttempt | attempt ID; job ID/version; node ID/generation; разрешённый render plan; стадия; время; количество/идентификаторы подтверждённых частей; error/uncertainty. |
| PublicationPart | attempt ID; порядковый номер API-вызова; request digest; before-send timestamp; итоговые message ID либо unknown. Секреты и тела файлов не журналируются. |
| AIWorker | UUID; имя машины; provider; capabilities; модель/каталог; last seen; status; credential hash; revoked timestamp. |
| AI task extensions | task kind (`news`/`title_translation`); operation ID; worker/model snapshot; lease generation; deadline; результат; version исходного Job. |
| AdminCredential | internal user ID; password hash; credential revision; changed timestamp. Нет открытой регистрации и пароля по умолчанию. |
| AuditEvent | actor (user/worker/system); действие; IDs; версии до/после; исход/причина; время. Секретные значения не включаются. |

AI task extensions можно добавить к существующей `news_tasks` с совместимым `kind=news`. Не создавать две независимые очереди, которые могут одновременно выдать одну новость. Operation показывает ход работы; lease/результат принадлежат task, публикационный статус — Job. Изменения связанных записей фиксируются одной транзакцией либо через устойчивое outbox-событие с дедупликацией.

Для создающей новость task обеспечить уникальную связь с результирующим Job (например, nullable unique `jobs.origin_ai_task_id`); не полагаться только на предварительный SELECT. Аналогично каждый элемент batch-import имеет устойчивый ключ результата. Для переводящей task результат относится к Job.version/исходному полю и сам по себе новый Job не создаёт.

### 1.3. Данные узла отдельно от контента

В приватной папке host: `node.json` (node ID, роль, пути, generation, разрешённый snapshot), `control.sqlite` (миграции, контрольные точки, сессии, локальные действия), хранилище секретов и квитанции активации. Эти файлы не копируются поверх идентичности другого узла вместе с БД контента.

Переносимые настройки отделены от машинных: каналы/интервалы/теги/язык относятся к системе; абсолютные пути, SSH, порты, локальный адрес LM Studio и service ID относятся к узлу. Выбор модели импортируется однократно из прежнего файла с привязкой к реальному worker; перезапуск не импортирует его заново поверх UI-настройки.

### 1.4. Транзакции и SQLite

- Короткие write-транзакции, внешние HTTP/AI/SSH вызовы вне транзакций; CAS по версии и атомарный claim канала. При необходимости `BEGIN IMMEDIATE` для сериализации изменения очереди.
- Включить foreign keys для каждого соединения, ограниченный busy timeout, согласованные WAL/checkpoint настройки и диагностику версии SQLite. Использовать поддерживаемый исправленный runtime, а не только проверять Python version.
- Нормализовать даты в UTC, включая старые naive значения по фактической прежней семантике. Не переинтерпретировать их часовым поясом ОС назначения.
- Добавить индексы для списка/фильтров/claim/операций; проверять планы на реалистичном наборе данных.
- Таблица идемпотентности не заменяет журнал отправок. Ключи опасных действий и неопределённые попытки сохраняются до разрешения; обычные завершённые receipts хранить минимум 30 суток. Уборка не удаляет доказательства миграции/отправки.
- Согласованный снимок SQLite создаётся Backup API; наличие WAL учитывается. [SQLite Backup API](https://www.sqlite.org/backup.html), [SQLite WAL](https://www.sqlite.org/wal.html).

## 2. Статусы и команды публикации

### 2.1. Job

Сохранить значения прежних статусов: `created`, `resolving`, `waiting_confirmation`, `queued`, `scheduled`, `downloading`, `processing`, `publishing`, `completed`, `failed`, `cancelled`. Новая модель фоновых операций не требует переименования старых состояний.

Основной путь: `waiting_confirmation → queued/scheduled → downloading → processing → publishing → completed`. `uncertain_publish` остаётся error code при `failed`, дополнительно связывается с незавершённой/частичной PublicationAttempt. В UI — отдельная заметная категория «Результат отправки неизвестен».

| Команда | Предусловия | Результат |
| --- | --- | --- |
| Изменить полный контент/альбом | waiting_confirmation, актуальная version | Та же запись, version + 1, устаревшая подготовка инвалидирована. |
| Изменить разрешённые поля очереди | queued/scheduled; не claimed; актуальная version | Обновление + новая version; расписание/очередь меняет QueueRevision. |
| В очередь | Готовый черновик, канал включён, нет неподтверждённого дубля/uncertainty | queued либо scheduled при заданной дате, одно место в очереди. |
| Точное время | Черновик/ожидающее задание, актуальная version | UTC дата сохранена; после подтверждения scheduled, queue_position=null. |
| Опубликовать сейчас | Черновик/ожидающее задание, readiness=true, все проверки допуска | Атомарная постановка/force, а не HTTP-отправка в Telegram в request handler. |
| Вернуть в черновик | Только ещё не claimed queued/scheduled | waiting_confirmation; снять позицию, force и активное расписание; прежнюю дату сохранить в аудите. |
| Отмена | Не completed | Ожидающее → cancelled; активное → cancel_requested и безопасная остановка. |
| Retry | failed, результат точно не отправлен, явное действие | Новая попытка обычной очереди; счётчик/ошибки по текущим правилам. |
| Повтор источника | Совпадение источника/канала подтверждено пользователем | Явный allow_duplicate; не отключает другие проверки. |
| Разрешить uncertain | Только отдельный сценарий сверки | Записать ручное заключение; отдельное подтверждение нового отправления при необходимости. |

Запрещённые переходы возвращают конфликт с текущим состоянием. Общий maintenance запрещает все изменяющие контент команды, кроме разрешённых завершений уже принятых операций на стадии drain. После freeze запрещены и они. Планирование переноса и чтение прогресса работают через host.

### 2.2. Единый допуск отправки

Перед отправкой проверяются: активная роль узла/поколение, gate, состояние Job, разрешённая версия/render plan, владение каналом, готовность данных. Force не меняет эти проверки.

Для многочастной отправки допуск выдаётся на целую публикационную сессию до первого сетевого вызова. Начало остановки атомарно закрывает выдачу новых допусков и фиксирует уже выданные. Эти сессии могут корректно закончить ранее начатую публикацию; UI в это время показывает «Останавливаем», а не «Все остановлено». Следующий API-вызов внутри сессии проверяет принадлежность действующему допуску. Произвольное продолжение старого процесса после отзыва запрещено.

Перед каждым вызовом Telegram сохраняется запись намерения; после ответа — известные message ID. Потеря ответа либо авария между успешной отправкой и сохранением результата переводит попытку в unknown. Не обещать exactly-once: внешняя отправка и локальная транзакция не атомарны. Известные части частичной отправки не теряются в общем исключении.

При timeout drain не убивать отправителя автоматически ради зелёной галочки. Показать ожидание/действие пользователя. При действительно умершем процессе зафиксировать неопределённые попытки, исключить их из автоматического повтора и только после проверки отсутствия живого отправителя разрешить перенос остальных данных.

## 3. HTTP API

### 3.1. Общие правила

JSON UTF-8; `/api/v1` для пользователя; `/api/worker/v1` для worker. OpenAPI строится из реальных моделей, клиентские типы генерируются/сверяются с ним. Инфраструктурные секреты и внутренний `post_data` целиком не сериализуются клиенту.

- GET не изменяет бизнес-данные и не запускает внешнюю обработку. Безопасные служебные access logs/сессии ведутся отдельно от контентного снимка.
- PATCH/действия с существующим объектом передают `expected_version`; отсутствие даёт 422, устаревшая версия — 409 `version_conflict` с безопасным актуальным DTO.
- Команды создания, импорта, постановки, ручной публикации, retry, backup и переноса требуют `Idempotency-Key` (UUID клиента). Одинаковый ключ+payload возвращает прежний результат; тот же ключ с иным payload — 409. Команда и receipt фиксируются атомарно. Незавершённая команда возвращает тот же operation ID.
- Длительное действие: 202 с `operation_id`, ссылкой состояния и созданным resource ID при наличии. Быстрое сохранение: 200. Создание короткого ресурса: 201. Отсутствие подходящей worker-задачи: 204.
- Ошибка: `{error: {code, message, retryable, field_errors, current_version, request_id, details}}`; необязательные поля отсутствуют/равны null. `details` содержит только разрешённые данные.
- 401 нет сессии; 403 нет права; 404 нет доступного ресурса; 409 версия/состояние/дубль; 413 размер; 422 валидация; 429 частота; 503 maintenance/runtime unavailable с причиной и operation ID, если есть. Клиент не повторяет опасный POST с новым ключом автоматически.
- Списки: `items`, `next_cursor`, `total` где вычисление допустимо, стабильная сортировка с ID как вторым ключом, limit по умолчанию 50, максимум 100. Фильтры валидируются.
- Время — ISO 8601 UTC с Z; выбранный timezone передаётся явно. `allowed_actions`/`blocked_reason` объясняют UI, но сервер повторно проверяет права при исполнении.

Внутренние authorize/activate endpoints узлов не доступны с обычным пользовательским токеном.

### 3.3. DTO и примеры

Минимальный PublicationDTO: `id`, `version`, `content_kind`, `status`, `error`, `title`, `source` (provider/id/url/author/date), `channel`, `tags`, `album` (selected/total/cover), `readiness`, `schedule` (kind/UTC/timezone/estimate), `last_operation_id`, `allowed_actions`, `updated_at`. Не выдавать provider cookies, download headers, локальные абсолютные пути файлов или bot token.

Пример сохранения: `PATCH /publications/125` с `{expected_version: 7, title: "Лунный сад", user_tags: ["art", "night"]}`. Ответ содержит version=8. Если Telegram уже изменил запись до version=8, PATCH возвращает conflict, а не version=9 поверх незамеченной правки.

Перестановка: `PUT /channels/2/queue/order` с `{expected_queue_revision: 14, ordered_job_ids: [125, 131, 126]}`. Передаётся полный набор обычных ожидающих заданий выбранного канала, полученный из отдельного актуального queue snapshot. Список одной страницы не считается полным набором. Активные/точно запланированные задания не включаются; неверный состав или claim между чтением и записью даёт 409.

Массовые операции: `{action, items: [{id, expected_version}], expected_selection_count}`. Отчёт по каждому элементу — success/conflict/blocked/not_found, без притворного общего успеха. Перестановка всегда целиком атомарна; массовый retry/отмена могут быть частичными с явным отчётом. `uncertain_publish` возвращает blocked.

`resolve-uncertain` принимает version и результат ручной проверки: `confirmed_sent`, `confirmed_not_sent`, `partial` или `still_unknown`, известные message IDs и примечание. Сохранить автора/время и происхождение подтверждения как ручное; не выдавать его за автоматическую сверку Telegram. `confirmed_not_sent` сам по себе не отправляет пост: повтор — отдельная команда с подтверждением. Partial остаётся заблокированным до решения по известным/неизвестным частям. Не реализовывать несуществующую возможность Bot API достоверно прочитать произвольную прошлую историю канала для такой проверки.

### 3.4. OperationDTO

Обязательные поля: `id`, `kind`, `status`, `stage_key`, `stages`, `version`, `created_at`, `started_at`, `updated_at`, `heartbeat_at`, `message`, `progress`, `result`, `error`, `allowed_actions`, `last_event_seq`.

Статусы операции: `queued`, `running`, `waiting_external`, `waiting_worker`, `waiting_user`, `cancelling`, `cancelled`, `failed`, `succeeded`. Статусы этапа: `pending`, `running`, `waiting`, `succeeded`, `failed`, `skipped`. `waiting_user` не равен failed; временная недоступность worker не означает ошибку модели.

`progress` = null при неизмеримом ожидании либо `{unit: "bytes"|"files"|"items", completed, total, percent, estimated_seconds_remaining}`. `percent=completed/total*100` только при total>0; процент относится к этапу. Файлы разного размера не позволяют выводить процент байтов из процента количества файлов. Итоговый процент всей миграции не обязателен.

Для AI показывать идентификатор worker, модель попытки, длительность и последнюю связь. При обработке частей источника можно показывать «3 из 8 частей», но не выдумывать процент внутренней генерации. Запоздалые/дублированные события не уменьшают sequence; после reconnect клиент загружает актуальный snapshot, затем события после sequence.

Принятая операция сохраняется до ответа 202. После restart нет вечных «running» без исполнителя: восстановление переводит в возобновляемый этап, waiting_user или failed с объяснением. Смена статуса и result ref согласована с фактическим созданием Job; повтор complete не создаёт второй черновик.

## 4. Медиа и предпросмотр

Каталог использует непрозрачный asset ID; пути вычисляет сервер внутри выбранного data root. Проверять traversal, Windows drive/UNC, symlink и выход из корня. Пользовательский filename — метаданные, не готовый путь. Загрузка ограничена конфигурацией, проверяется по содержимому/MIME, безопасно декодируется; распаковка экспортов дополнительно защищена от zip-slip/симлинков.

Оригиналы и подтверждённые подготовленные файлы immutable: новое содержимое получает новый storage key/hash, прежний файл не перезаписывается на месте. Это позволяет pin и копированию после краткого backup barrier сохранять согласованный набор. Сборщик удаляет только файлы без активных ссылок/pin.

Локальные файлы черновиков/очереди pinned до снятия всех ссылок. Очистка готовых временных файлов и воспроизводимых миниатюр отдельно от оригиналов. На время backup/миграции выбранный набор pin. Старое delete_after_publish не удаляет asset, нужный другому черновику.

Исторический файл может быть `missing`, thumbnail — `unavailable`, Telegram file ID — доступным для отправки без локального оригинала. Эти состояния различаются. Смена бота инвалидирует предположение о переносимости Telegram file ID. Для обычного переезда сохраняется тот же bot identity.

Повторный импорт старого альбома создаёт новый кандидат каталога, показывает различия и применяется с версией. Не перезаписывает ручные поля автоматически и не обещает восстановить удалённый источник. Если файл обязательной будущей отправки нельзя получить/проверить, readiness=false; прошлые публикации при этом остаются в истории.

RenderPlan связан с Job.version и версиями настроек, asset manifest и подготовленным переводом. Изменение содержимого/оформления инвалидирует план. План содержит безопасный текст/разрешённые entities и список частей отправки, а не произвольный HTML источника. Превью браузера и publisher читают один план. Видимые символы/Telegram entities проверяются сервером в соответствии с используемым методом.

HTTP выдача assets требует сессию/права. Не возвращать download URL Telegram, содержащий токен. Большой файл, который доступен через Telegram file ID, но не скачивается обычным Bot API, получает метаданные/миниатюру и объяснение, а не бесконечную загрузку. Лимиты методов проверять по [Bot API](https://core.telegram.org/bots/api#file) при реализации.

## 5. Авторизация и границы доступа

### SEC-02. Локальный вход

Host слушает 127.0.0.1/::1 по умолчанию. Launcher получает одноразовый случайный код (TTL 60 секунд), открывает bootstrap-адрес с кодом во fragment; JS обменивает его POST на сессию и удаляет fragment. Код одноразовый, не попадает в access logs/Referer, постоянный URL не является паролем. Привязка к существующему разрешённому администратору определяется настройкой установки; при нескольких администраторах настройка явная.

Host/Origin проверяются и локально; защита от DNS rebinding обязательна. HttpOnly cookie, SameSite=Lax либо строже; Secure обязателен для внешнего HTTPS, исключение только для локального HTTP. Изменяющие cookie-запросы требуют CSRF token и проверки Origin.

### SEC-03. Обычный внешний браузер

HTTPS, существующий администратор + пароль, сохранённый только как Argon2id-хеш. Первичная установка/сброс — через доверенный локальный launcher/SSH CLI, а не публичный «первый посетитель становится владельцем». Нет sign-up и стандартного пароля. Ограничение попыток, безопасное завершение сессии, отзыв после смены пароля. Web-администратор связан с тем же внутренним User.

Сессии сервера: случайный opaque token, хеш в control store, idle timeout 12 часов, absolute timeout 7 суток как настраиваемые начальные значения; чувствительное действие размещения/секретов требует свежего подтверждения личности (например, последние 10 минут), без повторного запроса на каждом шаге уже начатой миграции. Проверенные локальный код/Telegram-вход считаются подтверждением личности для соответствующей сессии.

### SEC-04. Mini App

Запуск кнопкой меню/кнопкой в личном чате по HTTPS. Backend валидирует исходную `initData` по официальному алгоритму и bot token, использует constant-time comparison, проверяет `auth_date` (начальный предел 5 минут и допустимый clock skew 30 секунд) и allowlist Telegram ID. Это выбранные пределы приложения, а не универсальные требования Telegram. `initDataUnsafe`, query user ID и наличие WebApp JS не подтверждают пользователя. [Официальная проверка](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

Обмен initData создаёт отдельную короткую сессию Mini App. Для совместимости WebView/встраивания разрешён opaque bearer, хранимый только в памяти страницы: idle 1 час, absolute 12 часов, отзыв на сервере, без localStorage/URL. Закрытие и новый запуск получают свежие initData. Клиент создаёт случайный exchange nonce и повторяет потерянный HTTP-запрос с тем же nonce. Replay cache связывает digest initData с nonce/сессией: идентичный обмен идемпотентен, новый nonce для уже использованного digest отклоняется с предложением переоткрыть приложение. Для возврата того же opaque token краткий ответ обмена хранится защищённо только на окно обмена; долгосрочная таблица сессий хранит хеш. Проверить допустимый сетевой retry и посторонний replay раздельно.

Там, где WebView принимает безопасную HttpOnly session cookie, использовать её для переживания обычного reload. Для bearer fallback несекретный exchange nonce можно сохранить в sessionStorage на короткое окно обмена; сам token/initData туда не сохранять. Если reload уничтожил bearer и initData уже устарели, показать повторный вход/переоткрытие Mini App. После входа восстановить прежнюю операцию: повторная авторизация не создаёт новую задачу и не отменяет существующую.

Bearer Mini App и cookie браузера проходят одинаковую проверку прав. Telegram initData не превращается в постоянный пароль. Возраст модели/состояние очереди не выводятся из данных Telegram — запрашиваются у backend.

### SEC-05. Worker и controller

Worker регистрируется одноразовым pairing code и получает отдельный случайный credential; сервер хранит хеш. Scope только capabilities/lease/progress/result; запрещены публикация, настройки, просмотр SSH, выдача всех медиа и произвольное управление. Учётные данные controller для связи узлов отдельны от worker и пользовательских сессий, привязаны к system/node/migration.

В maintenance вход/проверка сессии не обновляет User.last_seen_at или другие поля контентной БД после freeze. Актуальность сессии и безопасные access events обновляются в control store; проверка разрешений использует доступное чтение/зафиксированный контекст уже авторизованной управляющей операции.

Публичный reverse proxy не пропускает клиентский X-User-ID/служебный контекст как доверенный. Внутренний runtime принимает только локальный аутентифицированный transport от host; application layer всё равно проверяет активность пользователя и разрешение действия.

### SEC-06. Защита ввода и секретов

Сохранить PublicOnlyResolver и существующие запреты источников; дополнительно проверить redirects/DNS rebinding, loopback/private/link-local/cloud metadata и прокси-маршруты. Исключение для настроенного локального AI — отдельный административный allowlist, не общий обход SSRF для пользовательских URL. Текст источника и AI-ответ недоверен: безопасное форматирование, schema validation, отсутствие исполнения инструкций из текста.

Отключить wildcard CORS с credentials; CSP и frame policy совместить с проверенными способами открытия Telegram, а не бездумно запретить Mini App через DENY. Не включать открытый iframe embed для произвольных сайтов. Все секреты редактируются write-only; SSH пароль/ключ не хранится в localStorage, не включается в контентную SQLite и не отражается в progress/error.

## 6. Worker и приём Telegram

Worker v1: регистрация/heartbeat/capabilities, lease, progress, complete, fail, release/cancel acknowledgement. Lease включает task ID, token, system generation, model snapshot, срок, capability/type. Старый lease после migration/reassignment/cancel не может изменить Job. Повтор complete с тем же подтверждённым результатом возвращает прежний Job ID.

Минимальные маршруты: POST `/api/worker/v1/register` (pairing code), POST `/heartbeat`, PUT `/capabilities`, POST `/tasks/lease`, POST `/tasks/{id}/{progress,complete,fail,release}` в том же prefix. Register одноразов; остальные требуют worker credential, а task-команды — ещё lease token/generation. Complete проверяет digest результата и уникальную связь с Job. Heartbeat продлевает только действующую разрешённую lease в пределах политики; не оживляет отозванную. Лимиты размеров payload и таймауты задаются явно; file upload использует отдельное ограниченное разрешение на конкретный asset/task.

Старые `/api/news/tasks/lease`, `/{id}/progress`, `/{id}/complete`, `/{id}/fail`, `/api/news/health` временно обслуживаются адаптером на общем сервере. Они не используют browser auth и получают только задачи news; их отключение возможно после обновления зарегистрированного worker и отражается в инструкции релиза. Не запускать старый и новый lease dispatcher независимо.

Durable inbox: сохранить Telegram update и unique ID до его подтверждения следующим offset. Для группы обновлений сначала сохранить принятую группу, затем сдвинуть offset. Перезапуск повторно обрабатывает не завершённые записи идемпотентно. Не считать стандартный запуск обработчика в asyncio-task достаточной гарантией приёма.

Сборка пересланного альбома опирается на сохранённые части/media_group_id и контролируемое окно завершения. При остановке drain заканчивает сборку либо сохраняет продолжение; не теряет элементы в памяти. Чат-мастер должен создавать постоянный intake draft/operation достаточно рано; неполученный от пользователя текст восстановить невозможно.

Во время freeze polling остановлен, уже принятые update находятся в снимке. На назначении продолжается сохранённый offset/inbox; нельзя использовать drop_pending_updates. У Telegram ограниченный срок хранения необработанных обновлений, поэтому многочасовой/суточный простой не объявлять безусловно бесшовным. [Bot API: получение обновлений](https://core.telegram.org/bots/api#getting-updates).

## 7. Официальные опорные материалы

FastAPI lifespan использовать для явного управления ресурсами в каждой роли, не для безусловного запуска пула при каждом создании приложения: [Lifespan Events](https://fastapi.tiangolo.com/advanced/events/). Один polling на bot token не является защитой от двух исходящих отправителей: [aiogram long polling](https://docs.aiogram.dev/en/latest/dispatcher/long_polling.html). Точные внешние ограничения перепроверяются агентом на этапе реализации; новый контракт обязан сохранять описанные инварианты.

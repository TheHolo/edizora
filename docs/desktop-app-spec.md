# Edizora: отдельное desktop-приложение

Дата: 2026-10-28. Статус: проектное решение и ТЗ, реализация не начата.

## 1. Решение

Создать Windows-приложение на **Tauri 2 + React 19 + TypeScript strict + Vite**, сохранив Python/FastAPI/SQLite и существующий механизм публикаций. Пользователь запускает ярлык и получает собственное окно, трей, файловые диалоги и работающую фоновую очередь. Браузер для основной работы не открывается. Внутри окна используется системный WebView2: это desktop-приложение с веб-технологиями интерфейса, а не интерфейс из нативных WinUI-виджетов.

Первая целевая платформа — Windows 11 x64. Windows 10, ARM64, macOS и Linux не объявлять поддержанными без отдельных проверок. Предположение основано на текущем Windows-установщике проекта.

React/TypeScript выбраны за соответствие существующему коду, типизированные контракты, развитые средства проверки и небольшие изолируемые задачи для агента. Нет подтверждённого универсального рейтинга, по которому ИИ лучше всего программирует именно этот стек. Rust ограничить небольшим слоем интеграции с ОС; бизнес-логику туда не переносить.

### Сравнение вариантов

| Вариант | Преимущество для проекта | Цена / ограничение | Решение |
| --- | --- | --- | --- |
| Tauri 2 + React | Сохраняет frontend, использует системный WebView, поддерживает sidecar | Rust, WebView2 и отдельные desktop-тесты | Основной |
| Electron + React | Общий TypeScript для оболочки и UI, удобная экосистема | Собственный Chromium/Node увеличивает поставку; фактическую RAM нужно измерять | Резерв при доказанном блокере Tauri |
| PySide6/QML | Python-интеграция и отдельное окно | Переписывание React-интерфейса и другая модель UI | Не выбирать для этой миграции |
| WinUI 3 / .NET | Глубокая Windows-интеграция | Новый язык/стек и повторная реализация UI | Не оправдано текущей задачей |
| PWA | Минимум изменений | Сохраняет зависимость от браузерной модели установки | Не отвечает выбранному направлению |

Tauri сам по себе не гарантирует высокую скорость: Python, обработка изображений и React тоже входят в стоимость приложения. Выбор подтвердить прототипом и измерениями до массового изменения экранов.

### Состав стека

| Слой | Решение |
| --- | --- |
| Desktop | Tauri 2, Rust stable, минимальные capabilities, single-instance, tray, dialog |
| Frontend | Существующие React 19, TypeScript strict, Vite; npm и package-lock сохранить |
| Компоненты | Radix Primitives для сложных доступных контролов, CSS Modules + CSS variables; сохранить Lucide |
| Маршрутизация | React Router в декларативном режиме; hash history для bundled desktop, совместимый web-адаптер |
| Серверное состояние | TanStack Query 5: общий cache, отмена запросов, контролируемое обновление |
| Формы | React Hook Form + Zod для новых сложных форм; backend остаётся окончательным валидатором |
| Большие списки | TanStack Virtual + серверная пагинация; виртуализация по необходимости |
| Локальное состояние | useState/useReducer; не вводить глобальное хранилище без конкретной общей задачи |
| Контракты | Существующий OpenAPI + openapi-typescript; валидируемые IPC DTO, без ручных копий API-моделей |
| Backend | Существующие Python/FastAPI/SQLAlchemy/SQLite, host/runtime/worker |
| Поставка | PyInstaller onedir sidecar, Tauri shell, существующий Inno Setup как единый установщик |

Не добавлять Next.js/SSR, второй Node-сервер, Redux или второй UI-kit без обоснованной потребности. Точные совместимые версии новых библиотек зафиксировать в lock-файлах на этапе прототипа; текущие версии не обновлять массово одновременно с миграцией.

## 2. Исходное состояние и границы

Проверено в checkout:

- `frontend/package.json`: React 19.1.1, TypeScript 5.9.3, Vite 7.3.7, уже есть генерация API.
- `frontend/src/App.tsx`: общий интерфейс публикаций, очереди, календаря, AI, каналов, размещения и настроек.
- `frontend/src/hooks.ts`: собственные query hooks с polling; общую отмену/дедупликацию и политику cache следует централизовать.
- `frontend/src/api.ts`: same-origin HTTP, session/CSRF, idempotency, upload и защищённые медиа. Простое помещение в WebView изменит origin и сломает эти предположения.
- `app/desktop/launcher.py`: первый запуск через `webbrowser.open`, затем передача управления `app.web`; есть `--background`, блокировки и восстановление незавершённой установки.
- `app/desktop/tray.py`: существующий Python-трей. В новом desktop-режиме должен остаться один владелец трея.
- `app/desktop/routes.py`, `app/host`, `app/runtime.py`: повторно использовать авторизацию, SecretStore, управление процессами и защиту отправителя.
- `deploy/build-desktop.ps1`, `deploy/edizora.spec`, `deploy/edizora.iss`: существующая цепочка выпуска.
- `tests/test_desktop.py`, `tests/test_desktop_bundle.py`, `tests/test_desktop_installer.py`: сохранить и адаптировать регрессии.

Это архитектурное обследование, не полный аудит корректности и не измерение производительности. Старые `web-platform-*.md` сохраняют значение для серверных функций; в части запуска desktop, оболочки и транспорта приоритет имеет это ТЗ. Web/Mini App не удалять: общий frontend использует отдельный адаптер окружения.

## 3. Архитектура и процессы

```text
React UI (bundled assets, WebView2)
  -> типизированный DesktopTransport / Tauri invoke
  -> узкий Rust bridge (проверка команд, session, lifecycle)
  -> локальный Python sidecar / существующий host
  -> runtime -> SQLite / Telegram / AI workers

Web/Mini App -> WebTransport -> существующий HTTP API
```

Frontend — представление и пользовательское состояние. Rust — окно, tray, интеграция ОС, транспорт. Python — права, данные, задания, расписания и отправка. Renderer не читает SQLite и не выполняет shell-команды.

### Запуск и завершение

1. Shell сразу показывает окно состояния загрузки; работу с диском/процессами выполняет вне UI thread.
2. Один экземпляр shell на профиль установки. Повторный запуск поднимает существующее окно; существующие host/runtime locks остаются обязательными.
3. Sidecar получает только фиксированный режим запуска и проверенный data-root. Запускать скрыто, без терминала, без зависимости от checkout или установленного у пользователя Python/Node/Rust.
4. Добавить режим backend без браузера и Python-трея, включая первый запуск. Не ограничиваться существующим `--background`, потому что мастер настройки сейчас отдельно открывает браузер.
5. Bootstrap через защищённый локальный канал: nonce запуска через stdin/pipe, ready-сообщение с версией протокола, PID, адресом и идентичностью установки. Секреты не передавать через argv, URL или логи. Соединение только с подтверждённым loopback endpoint; backend слушает `127.0.0.1`, порт назначается bind на 0, а не поиском свободного порта с последующим повторным bind.
6. Для уже работающего host использовать существующий control store и проверку идентичности/прав локального пользователя. Одного совпадения PID или порта недостаточно. Не создавать второй scheduler при переподключении.
7. До ready показывать стадии; через 30 секунд показывать диагностируемую ошибку и «Повторить». Не рисовать фиктивный процент выполнения.
8. Крестик по умолчанию скрывает окно в трей; при первом закрытии объяснить, что очередь продолжает работать. «Выйти и остановить» запускает штатный drain. Если завершение задерживается, показать состояние; не убивать отправитель автоматически по таймеру.
9. После аварии shell допускается оставшийся единственный host; новый shell переподключается. После аварии host — ограниченный backoff, явная ошибка, восстановление штатным протоколом. Не переотправлять неизвестный результат публикации.
10. Автозапуск запускает shell в трее; управление фоновым host остаётся единственным. Shutdown Windows, sleep/resume и восстановление окна за пределами отключённого монитора покрыть проверками.

### Транспорт и безопасность

Выбран bridge через Rust к локальному HTTP API. До переноса экранов доказать полный маршрут login -> список -> mutation -> upload -> media -> logout. Не загружать удалённый сайт как привилегированное окно Tauri.

- Определить интерфейс `ApiTransport`: JSON-запросы, upload с прогрессом/отменой, получение медиа, отмена request ID. WebTransport сохраняет обычный HTTP; DesktopTransport использует IPC.
- Rust принимает ограниченный перечень операций/шаблонов путей и методов из API-контракта. Запрещены произвольные URL, `..`, `file:`, redirects на другие origins, пользовательские Authorization/Host и административный `/_host/*` через общий proxy.
- Отдельные узкие lifecycle-команды, доступные только основному локальному окну; аргументы валидируются Rust и backend. Минимальные capabilities; не выдавать renderer универсальный shell/fs/http доступ.
- Bootstrap credential подтверждает транспорт, но не заменяет вход пользователя. API продолжает проверять actor, CSRF, fresh-login, ограничения ресурсов и Idempotency-Key. Не отключать защиты глобально ради нового origin. Для desktop явно определить проверку доверенного локального транспорта; web-проверки сохранить.
- Session credentials хранить в памяти bridge, очистить при logout/завершении; секреты бота/AI остаются в существующем SecretStore. Не сохранять их в localStorage, TanStack cache или диагностике. «Запомнить вход» вне первого релиза.
- IPC ошибки возвращать в общем формате API с request ID; отмена чтения прекращает работу, отмена ожидания mutation не означает отмены серверной операции. Не повторять опасные mutations автоматически.
- Большие медиа не кодировать в base64 JSON. Native file picker выдаёт ограниченный handle для streaming upload; drag-and-drop проходит ту же валидацию. Для preview реализовать защищённый поток бинарных данных/custom protocol с непрозрачными resource ID и ограничением cache, без произвольных файловых путей. Проверить revocation при logout и очистку временных файлов.
- CSP без удалённых скриптов и eval, bundled шрифты/ассеты, запрет произвольной навигации. Пользовательские ссылки `https/http` открывать внешним браузером только по явному действию; остальные схемы отклонять.

## 4. Функциональные требования

| Область | Обязательное поведение |
| --- | --- |
| Первый запуск | Создание установки, импорт legacy, восстановление backup внутри окна; существующая staging/recovery логика |
| Вход | Вход, выход, истечение сессии, повторное подтверждение чувствительных действий; cache очищается при смене пользователя |
| Публикации | Поиск, фильтры, пагинация, список/сетка, выбранный канал, сохранение позиции при возврате |
| Редактор | Текст/изображения/альбом, порядок и обложка, preview, валидация, состояния сохранения и конфликтов |
| Очередь | Пауза, возобновление, изменение порядка, статусы и ошибки, защита от повторного действия |
| Календарь | Часовой пояс явно виден; существующая семантика дат и расписания сохранена |
| AI | Профили, проверка подключения, ход задачи, результат и ошибки; обработка не блокирует редактор |
| Каналы | Список, права бота, основной канал, доступные статистики |
| Эксплуатация | Настройки, backup/restore, размещение/перенос, журнал операций и диагностика доступны в приложении |
| Desktop | Трей, single-instance, native dialogs, настройки автозапуска, сохранение размера/позиции окна |

UI: сохранить узнаваемость Edizora и существующие RU/EN-переводы. Общие токены цвета, отступов и типографики; светлая/тёмная/системная тема. Sidebar + рабочая область + контекстная панель редактора. Нативные рамки окна в первом релизе. Проверить 1280×720 и 1920×1080 при масштабе 100/150/200%; панели должны адаптироваться, а не прятать кнопки.

Клавиатура: Tab/Shift+Tab, Escape для dismiss, Ctrl+S для сохранения, Ctrl+K для навигации. Видимый focus, корректные labels, trap/return focus в диалогах, reduced motion. WCAG AA для контраста. Empty/loading/error/offline/permission/conflict — полноценные состояния каждого рабочего экрана.

Локальный backend работает без интернета, но Telegram/облачный AI показывают недоступность. Не обещать отправку без сети. Для несохранённого текста — локальный recovery draft в app-data с ID пользователя/публикации и базовой версией; восстанавливать после сбоя с предложением сверки, не затирать серверную правку. Не хранить пароли/токены вместе с draft. Явные состояния «изменено», «сохраняется», «сохранено», «нет связи», «конфликт».

## 5. Отзывчивость и бюджеты

Ниже целевые критерии, а не уже полученные результаты. Эталон: Windows 11 x64, 4 физических ядра, 16 GB RAM, SSD, 1920×1080/100%, production build, WebView2 и версии ОС записаны в отчёте. AI inference и загрузка сети измеряются отдельно.

| Метрика | Критерий |
| --- | --- |
| Первое видимое окно | p95 ≤ 1 секунды после запуска процесса |
| Готовность к работе при настроенной установке | p95 ≤ 3 секунд на тёплом запуске, ≤ 5 секунд на холодном, без ожидания внешней сети |
| Реакция кнопки/ввода | p95 ≤ 100 ms до видимого feedback; ввод редактора ≤ 50 ms |
| Открытие ранее загруженного экрана | p95 ≤ 150 ms, без общего пустого экрана |
| Прокрутка списка | p95 frame time ≤ 20 ms в 30-секундном прогоне, без пауз > 100 ms |
| UI main thread | Нет задач > 100 ms при вводе, навигации и прокрутке типового набора |
| Покой, без активных задач | Средний CPU дерева процессов < 1% за 60 секунд после прогрева |
| Память | Цель ≤ 350 MiB private bytes всего дерева shell/WebView/backend в покое без AI; отдельно зафиксировать peak |
| Утечки | После 30 циклов открытия/закрытия редактора нет монотонного роста; после стабилизации прирост ≤ 30 MiB |

Данные: 10 000 публикаций, 20 каналов, 1 000 записей очереди, реалистичные thumbnails и альбомы; генерируемые fixtures, никаких рабочих токенов. Для старта — 20 тёплых и 10 холодных запусков (после перезагрузки для холодных), для действий — ≥100 измерений. Записать сырые результаты, p50/p95, размеры bundles/installer, версии и характеристики машины. Не выдавать WebView-only RAM за расход всего приложения. При превышении бюджета — профиль, причина и исправление либо явно согласованная корректировка критерия.

Практики реализации:

- Lazy-load маршрутов и тяжёлых редакторов. Начальный JS budget ≤ 250 KiB gzip (учёт gzip для сравнения сборок, даже при локальной поставке).
- Серверная фильтрация/пагинация. В DOM только видимые элементы плюс overscan; изображения — thumbnails с размерами и lazy decode. Не скачивать оригиналы для списка.
- Query cache по пользователю/каналу/фильтрам; ограничение размера/времени жизни, адресная invalidation. Отмена устаревших поисков и защита от гонок ответов.
- Для активной очереди polling порядка 2 секунд, для настроек — длинный staleTime. При скрытом окне остановить UI polling; scheduler работает независимо. После focus — один deduplicated refresh. Точный интервал подтвердить нагрузочным замером.
- В v1 сохранить существующие operation events через HTTP polling. Не считать их готовым SSE. Push/SSE добавлять только при измеренной необходимости.
- Optimistic UI только для обратимых изменений с rollback. «Опубликовано», завершение backup/restore и перенос показывать после подтверждения backend.
- Обработку медиа/AI не выполнять на renderer thread. Мемоизация по данным профилирования; не добавлять memo/useMemo повсюду.

## 6. Поставка и миграция

Сохранить data-root, идентичность установки, SQLite, SecretStore, очередь, расписания и существующие backup/restore. Первый запуск новой оболочки не должен инициализировать пустую БД поверх существующей. Изменения схемы — отдельная миграция и совместимость; переписывание данных из-за выбора frontend не требуется.

Inno Setup устанавливает Tauri shell как `edizora.exe`, backend — отдельным приватным executable в bundle. Исключить конфликт имён, Python-трей и двойные ярлыки. На машине пользователя не нужны dev-инструменты. WebView2: проверка наличия, понятная установка runtime; для офлайн-установки предусмотреть включённый offline installer. Его размер учитывать отдельно.

Перед обновлением — штатная остановка и backup. Installer обязан уважать отказ/задержку drain, не завершать процесс принудительно. Проверить обновление с текущей сборки, повторный запуск, удаление с сохранением данных и повторную установку. Откат бинарников допустим только при совместимой схеме; иначе восстановление совместимой копии по явной процедуре, без скрытой потери новых данных.

CI собирает frontend, sidecar и shell, запускает проверки, выдаёт установщик, hashes, manifest версий и лицензии. Подпись кода требует доступного сертификата: при его отсутствии выпуск обозначить неподписанным. Автообновление, macOS/Linux и новый cloud-backend за рамками первого релиза.

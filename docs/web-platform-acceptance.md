# Приёмка и план проверок веб-версии Edizora

Приложение к [ТЗ](web-platform-spec.md), версия 1.0 от 25 октября 2026 года. Это перечень необходимых проверок будущей реализации, а не отчёт об уже выполненных тестах.

## 1. Подготовка и доказательства

QA-01. До изменений сохранить текущее рабочее дерево с незакоммиченными/новыми файлами, согласованный snapshot SQLite, обязательные media и приватную конфигурацию отдельно. Составить baseline report: release/tree hash, schema, число/ID/статусы сущностей, очереди и даты UTC, message IDs, источники, отсутствующие файлы, старые JSON-форматы, настройки AI и запусков. Не включать секреты в отчёт.

QA-02. Все автоматические тесты используют отдельные каталоги, fake Telegram/AI/SSH и временные SQLite. Не запускать реальный polling/publisher или запрос AI на рабочем профиле. Скопированная БД для теста не получает production credentials. Публикации для smoke-test — только в явно согласованный тестовый канал.

QA-03. Основные существующие suites сохранить: очередь/расписание/recovery/publisher, bootstrap/local runtime, album editor/UI, news API/pipeline/worker, providers/download/media, translation/caption/models, logging/security. Историческое число прошедших тестов из docs не считается результатом текущей проверки. Если baseline уже содержит ошибку, зафиксировать её до изменения и показать отношение к новой работе.

QA-04. Для каждого этапа в отчёте: build/commit или tree hash, окружение, проверенные требования, команды/сценарии, фактические результаты, ссылки на отчёты/скриншоты и непроверенные пункты. Нельзя помечать external smoke выполненным на основании mocks.

| T-U10 | SET-01 | Ошибка Telegram/AI/источника не выглядит как ноль подписчиков или «всё здорово»; показаны последнее успешное значение и его возраст. |

## 4. Подробные сценарии наиболее опасных сбоев

### A. Начало переноса во время отправки

1. Fake Telegram удерживает ответ уже начатой отправки; одновременно запросить migration start и publish-now другого Job из двух интерфейсов.
2. Новая команда отклоняется/ожидает maintenance согласно API, новый permit не выдан. UI показывает stopping и одну активную сессию.
3. Завершить Telegram ответ, сохранить message IDs; если публикация состоит из нескольких частей, завершить её в рамках ранее выданного permit.
4. Только после сохранения результата и отсутствия writers перейти в quiesced. Снимок содержит результат, target не повторяет этот Job.
5. Повторить с потерей ответа: uncertainty сохранена; после проверки смерти/завершения отправителя перенос допустим, автоматический retry невозможен.

### B. Потерянное подтверждение активации

1. Source retired; controller устойчиво записал grant; target сохранил grant и активную роль, сохраняя migration gate.
2. Оборвать ответ target. Перезапустить controller и попытаться запустить старый source launcher.
3. Source не публикует; controller запрашивает target по migration ID и получает прежнюю квитанцию либо остаётся в recovery_required.
4. При известном active target продолжить routing/check и снять только migration gate. Ни одного нового grant другой машине и ни одного rollback на старую БД.

### C. Возврат после изменений в облаке

1. Выполнить Windows → Ubuntu; в облаке добавить черновик, изменить настройки, опубликовать тестовое задание и получить message IDs.
2. Выполнить Ubuntu → Windows через зарегистрированный Windows host за NAT.
3. Сверить новые/старые IDs, контент, расписание, результаты и файлы. Старый локальный набор архивирован; публикация из пункта 1 не появилась второй раз.

### D. Неподтверждённые внешние действия

Инъекция сбоя до API-вызова, после фактической отправки до ответа, после ответа до DB commit и после commit до HTTP-ответа UI. Для каждого случая зафиксировать, известен ли результат. Идемпотентность UI не должна маскировать неизвестную отправку Telegram. Проверить также альбом и медиа+отдельный текст новости.

### E. Заморозка полного состояния

Создать одновременно открытый HTTP PATCH, обработчик Telegram update, pending album debounce, news finalizing, статистику и очистку файлов. Начать перенос. Доказывать quiescence реальными barrier/счётчиками, а не задержкой sleep. После freeze snapshot и manifest не меняются, control progress обновляется, все принятые до границы данные находятся в пакете.

## 5. Прерывания на границах этапов

Автоматически проверить остановку controller до и после commit каждой контрольной точки: stopping, quiesced, preparing_target, snapshotting, transferring, verifying, retiring_source, activation_committed, activating_target, routing, completed. Для каждой комбинации записать допустимые роли source/target, наличие snapshot/grant/receipt и ожидаемое следующее действие.

Общие инварианты: не больше одного владельца отправки; нет отправок при migration gate; source не оживает после committed handoff; не потеряны подтверждённые данные; unknown не повторяется; незавершённый staging не становится data root; повтор безопасного шага не создаёт второй эффект. Отдельно проверить повтор любого control request и устаревший plan revision.

## 7. Критерий готовности всего задания

- Все обязательные функции [основного ТЗ](web-platform-spec.md) реализованы и доступны из UI, включая Mini App и три направления переноса.
- Существующие пользовательские сценарии сохранены; отключения/изменения задокументированы и согласованы, не спрятаны за удалением Telegram-команд.
- Обновление реальной структуры БД на копии сохраняет ID/историю/очередь и даёт воспроизводимый отчёт.
- Нет автоматического обхода global gate, двойной активации или повтора uncertain; соответствующие сбои испытаны.
- Приложены реальные снимки реализованных экранов и результаты визуальной проверки по концептам.
- Поставка воспроизводима; установщик, запуск, backup/restore, worker и Mini App описаны для владельца.
- Нет неотмеченных проваленных проверок и критических TODO в требуемых путях. Каждое внешнее непроверенное условие названо конкретно.

Если реальный VPS/мобильный клиент/тестовый канал недоступен, агент завершает доступную реализацию и проверки, передаёт готовый проверочный сценарий и точно перечисляет остаток. Он не вправе объявлять весь продукт полностью проверенным. Отчёт «сделан MVP» не закрывает это ТЗ.

# Общие операции, данные и домашний AI

Отчёт реализации S1–S3/S5, 26 октября 2026. Это описание кода и автоматических
проверок; оно не заменяет итоговую матрицу приёмки и внешние испытания.

## Границы

`app/application/platform.py` содержит команды публикаций, очередь, CAS,
идемпотентность, операции, права внутреннего администратора, каналы, настройки,
историю, каталог и выдачу медиа. HTTP-адаптеры не вычисляют допуск публикации.
`app/api/extras.py` расширяет те же операции проверкой каналов, AI, импортом
конфигурации, календарём и переходным worker API.

Управляемый Telegram вызывает те же команды подготовки, проверки, enqueue и
ручной отправки. `PreviewService` сохраняет команды подготовки/личной проверки,
ожидает серверные операции и не запускает домашнюю модель на сервере. Стабильный
ключ, привязанный к update/job/этапу, предотвращает повтор личной отправки после
восстановления inbox. Сохранение полей из старых обработчиков подчиняется общему
maintenance gate; ORM проверяет исходную версию Job/Channel при UPDATE.

## Данные и сохранность

Последовательный журнал SQLite имеет три версии: распознанная прежняя схема,
платформенные сущности, постоянное состояние чат-мастеров. `create_schema` является
явной управляющей командой. Она делает Backup API копию файловой БД перед upgrade,
берёт `BEGIN IMMEDIATE`, проверяет известные базовые таблицы, запрещает более
новую/неполную текущую схему и выполняет транзакционные DDL. Существующие ID,
история и неизвестные поля JSON сохраняются. `news_tasks.origin_chat_id` допускает
NULL для веб-создания. На каждом соединении включены foreign keys, busy timeout и
WAL. Миграция не выполнялась на рабочей БД.

Job/Channel имеют монотонные версии: ORM optimistic locking плюс SQLite triggers
для старых SQL-команд. Версия проверяется до изменения; HTTP-команды пишутся в
сериализованной транзакции. Receipt и эффект команды фиксируются вместе.

После первого заполнения `config_seeded` запрещает автоматический импорт TOML,
включая появление новых alias. Изменения импортируются отдельным явным планом.
Это намеренно изменяет прежнее поведение resync. Фикстуры старой схемы теперь
действительно удаляют отсутствовавший в старой версии журнал перед upgrade.

## Публикация и подготовка

Активный узел передаёт `ControlStore` всем управляемым сервисам. Claims,
изменения, ручной force и личные проверки проходят gate. Перед первым Telegram
вызовом получается publication permit; внутри альбома проверяется тот же permit.
Пауза не превращает ещё не начавшуюся отправку в ошибку/новую попытку: такое
задание возвращается в ожидание. Уже начатый multipart завершается при drain.

`PublicationAttempt` и `PublicationPart` сохраняют намерение перед каждым API
вызовом и подтверждённые message IDs после него. Network timeout, частичная
отправка, Telegram success перед ошибкой commit и ошибка истории после success
дают `uncertain_publish`, который не повторяется автоматически. Известные части
сохраняются. Exactly-once для Telegram не заявляется.

Оригиналы/миниатюры и подготовленные варианты immutable и адресуются hash/asset ID.
Загрузка проверяет содержимое Pillow, размер и dimensions; пути отвергают traversal,
UNC/drive и symlink. Полные оригиналы не загружаются в списке публикаций: cover
использует только миниатюру. Идентификатор asset не раскрывает путь/Telegram token.

Подготовленная очередь читает сохранённый render plan и media manifest. Она не
обращается к домашнему AI или источнику перед отправкой. GET preview читает тот же
план. Изменение шаблона/тегов/режима канала инвалидирует подготовку ожидающих
публикаций; интервал/пауза не меняют content hash. Неподготовленная управляемая
очередь ждёт, а не отправляет старое содержимое.

## Операции и Telegram inbox

Операция сохраняется до ответа клиенту. Один runtime-owned `OperationRunner`
обрабатывает очередь; после restart безопасные этапы восстанавливаются, личная
проверка с неизвестным результатом требует ручной сверки. Импорт сохраняет
checkpoint каждого результата; retry не создаёт повтор успешных элементов.

`DurableDispatcher` сохраняет полученную группу update до следующего offset,
обрабатывает inbox последовательно и ожидает завершения сборщика альбома перед
отметкой processed. Приём создания черновика/AI-task дедуплицируется по update и
результату. `PersistentStorage` сохраняет чат-мастер. Не используется
`drop_pending_updates`.

Старые `app.main`/обычный запуск `app.local` отказывают при наличии managed env
или pointer `.publisher-managed.json`. Старый код, вручную запущенный вне этих
управляемых entrypoint, не становится безопасным резервом; его отключение на
реальной установке остаётся обязательным эксплуатационным шагом.

## AI и совместимость

`app/application/worker_protocol.py` использует единственную `news_tasks` очередь
для news/title_translation. Регистрация одноразовая, credential хранится хешем,
embedding-модели исключены. Lease требует фактически доступной модели; отсутствие
модели не расходует attempts. Модель зафиксирована в задаче/попытке. Старые lease,
отменённые/переназначенные задачи и чужое поколение отклоняются.

Повтор complete с тем же token/result возвращает прежний Job. Создающая задача
имеет уникальный `origin_ai_task_id`. Перевод относится к исходному Job.version;
при изменении черновика результат становится предложением. Он не заменяет ручное
поле автоматически. Пользовательские загруженные медиа добавляются к результату
AI и сохраняются через immutable JobAsset references.

Telegram-origin news после complete получает атомарную постоянную цепочку prepare
→ telegram_preview с детерминированными ID. Веб-задача с NULL origin не вызывает
неожиданную отправку в Telegram.

`legacy_worker_command` обслуживает старые `/api/news/*` с отдельным
NEWS_WORKER_TOKEN через тот же сервер и таблицу. Старый worker не получает
translation-задач, browser auth или bot token. Самостоятельный старый dispatcher
параллельно не запускается.

Новый исходящий клиент: `python -m app.worker_v1 --pair --server https://HOST
--provider lmstudio` (или `ollama`). Код вводится через getpass; credential хранится
в машинном SecretStore, а безопасный origin/system ID — отдельно. Клиент не следует
HTTP redirect, проверяет system ID и использует только локальный LM Studio/Ollama.
Изменение endpoint после переноса требует подтверждённой повторной привязки, если
не сохранён прежний доверенный адрес. Подписанное автоматическое переназначение
endpoint пока не реализовано.

## Просроченные даты и перенос

`deployment_readiness()` проверяет сохранённые планы и обязательные локальные
файлы очереди. `prepare_handoff` вызывается контроллером после drain, проверяет
роль/поколение/block owner, отзывает AI leases и записывает выбранную политику.
Точные даты остаются исходными. Catch-up использует последний реальный успех и
отдельный минимум 60 секунд на канал, не меняя обычный interval timer. Hold оставляет
решение человеку. Skip требует явного списка ID; новые неподтверждённые просрочки
удерживаются, а не отменяются. Target снова применяет политику при активном запуске.

## Проверки и пределы доказательств

Новые suites: `tests/test_web_core.py`, `tests/test_web_worker.py`,
`tests/test_web_telegram.py`. Проверены CAS/параллельные изменения, receipt retry,
read-only preview, force/global gate, неизвестные/частичные Telegram ответы,
success-before-commit failure, пути/содержимое upload, inbox replay, album drain,
restart чат-мастера, модель/lease/поколение, stale translation, worker pairing,
переходный API и managed entrypoint/menu. Отдельный тест доказывает общий
Telegram preview после повторной обработки update: одна фактическая fake-отправка.

Промежуточные результаты: 54 теста трёх новых suites; 99 тестов нового ядра вместе
с queue/news/album regression. После последующих изменений итоговое число и
полная команда фиксируются в основном журнале приёмки, а не подменяются этими
промежуточными числами.

Все отправки/AI в этих тестах заменены контролируемыми fake-объектами. Реальный
Telegram-канал, LM Studio/Ollama, клиенты Telegram Android/iOS/Desktop и машины
Ubuntu здесь не использовались. Их прохождение не заявляется. Отдельно нужны
испытания аварийного завершения настоящего процесса/альбома, реальных внешних
источников, registered worker через HTTPS и каждого направления переноса.

## Дополнительное ревью в исходном репозитории

Календарь вычисляет прогноз по полной компактной выборке метаданных очереди,
затем фильтрует дату и выдаёт не больше 100 записей страницы. Cursor сохраняет
опорное время прогноза и привязан к фильтру; старые записи недели не исчезают за
последними 100 созданными Job. Просрочки имеют отдельный счётчик и ограниченную
выборку. На синтетической очереди 10 000 Job проверена правильная страница после
8900 предыдущих интервалов; отдельный замер дал 177,72 мс на текущем Windows-хосте.
Это не измерение p95 на нормативном стенде 2 vCPU/4 ГБ.

AI DTO возвращает допустимые действия по состоянию. Активную попытку нельзя
переназначить/повторить; отдельный retry сбрасывает исчерпанные attempts. Выбор
AI создаёт ApplicationState при необходимости и сохраняет глобальные worker/model.
Новые web/Telegram/title задачи фиксируют выбранного исполнителя и модель;
lease фильтрует эту привязку до ограничения кандидатов. Смена выбора не меняет
уже начатую попытку. Отзыв выбранного worker не вызывает скрытого перехода на
другую машину: требуется явное переназначение. При отсутствии всякой v1-регистрации
сохраняется явно настроенный старый news-worker и его модель.

План импорта без явного списка читает текущие доверенные Settings и включает
только разрешённые поля каналов. Файловый путь из браузера не принимается,
инфраструктурные секреты в plan не попадают. Изменение оформления через config
import использует ту же инвалидизацию render plan, что редактор канала.
`list_channels`/`get_channel` восстанавливают последние сохранённые права бота и
последнюю успешную статистику подписчиков после reload, не подставляя нули при
ошибке сети.

Добавлен `tests/test_web_extras.py`. Финальное локальное ревью этого блока:
76 scoped тестов ядра/AI/календаря/news прошли; после последней проверки старого
worker отдельно прошли 22 worker-теста. Итоговая полная регрессия фиксируется
основным отчётом выпуска.

Дополнительно закрыто восстановление оставшихся permits после смерти runtime:
`app.operations.recovery.recover_orphaned_permits` допускается только при реально
захваченном OS lock конкретной установки, до запуска исполнителей. Сначала одна
транзакция контента фиксирует неопределённые попытки/части и блокировку повторов;
лишь после её commit очищаются permits в control store. Подтверждённая Publication
с согласованными message IDs сохраняет завершённый результат. Личная проверка,
оборванная на sending, требует сверки человеком. Повтор после ошибки между двумя
хранилищами идемпотентен. История API возвращает известные ID по каждой части без
внутренних путей render plan и без произвольного текста исключений.

`tests/test_web_recovery.py` проверяет отдельный настоящий процесс, удерживающий
OS lock: пока он жив, восстановление недопустимо; после его остановки требуется
реальное получение освобождённого lock. Также проверены оба порядка ошибки commit,
сохранение подтверждённых частей, доказанная завершённая Publication и неизвестная
личная проверка. Это процессное испытание Windows с тестовыми данными, а не
реальная отправка Telegram или испытание Ubuntu.

AI task DTO теперь содержит `version` из lease_generation. Изменяющие команды
требуют expected_version; захват новой lease, действие и терминальный переход
повышают версию. Stale UI получает 409. Отмена общей Operation отзывает связанную
AI lease; её retry действительно возвращает failed task в очередь. Повторная
обработка сохранённого Telegram update использует идентичность исходного ввода,
а не более поздний выбор worker/model или канала.

Последняя проверка блока восстановления/CAS: 89 комбинированных тестов прошли;
после уточнения stable receipt отдельно прошли 67 тестов core/worker/recovery.

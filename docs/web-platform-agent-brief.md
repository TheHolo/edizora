# Стартовое поручение реализующему ИИ-агенту

Требуется реализовать новую веб-версию существующего Edizora в этом репозитории по полному комплекту технического задания. Это отдельная задача реализации; подготовка документов сама по себе не запускает переделку или публикации.

Сначала прочитай:

1. [Основное ТЗ](web-platform-spec.md).
2. [Контракты](web-platform-contracts.md).
3. [Перенос и эксплуатация](web-platform-migration.md).
4. [Дизайн и восемь макетов](web-platform-design.md).
5. [Приёмку](web-platform-acceptance.md).

Далее проверь актуальные AGENTS.md, рабочее дерево и текущий код. Основа — все существующие изменения, включая незакоммиченные и новые файлы, а не только последний коммит. Не откатывай чужую работу. Создай безопасный снимок/план реализации и журнал исполнения с привязкой к S0–S8 и ID требований/проверок.

Целевой результат: общий FastAPI backend, React/TypeScript веб-панель и Telegram Mini App, текущая SQLite с управляемыми миграциями, работающие редакторы/очередь/AI/каналы/история, тёмный интерфейс по макетам, сохраняемый прогресс, Windows-установка и Ubuntu 24.04 LTS, мастер Windows ↔ Ubuntu и Ubuntu → Ubuntu с общей остановкой всех публикаций и проверенной передачей единоличного управления.

Переиспользуй существующие сервисы. Сначала выдели общие команды/модель данных и устойчивое исполнение, затем API и UI. Все интерфейсы обязаны проходить одни проверки. Сохрани Telegram-приём материалов и команды как клиентов общей логики. Не дублируй правила публикации в компонентах React и роутерах.

Работай этапами с регрессионными проверками. Завершение локальной панели — промежуточный результат, а не конец задания. Не заменяй реальный backend статическими mock-данными, фиктивным прогрессом или кнопками без действия. Все три направления миграции входят в итог.

Рабочую БД/боевые токены не использовать для тестовых отправок. Разрабатывай и проверяй на изолированных копиях и тестовых конфигурациях; внешние публикации и изменение реального размещения выполнять только в разрешённом окружении. Подготовь конкретный план/сборку до запроса необходимых доступов. Не выводи секреты в отчёты.

Особо проверь: force не обходит migration gate; начатые отправки завершаются до снимка; неизвестный результат Telegram не повторяется автоматически; source после handoff не запускается вновь; потеря ACK target не вызывает rollback; возврат из облака использует актуальную облачную БД; AI дома независим от очереди на VPS; закрытие вкладки не прекращает принятую операцию.

Рутинные решения принимай самостоятельно в рамках ТЗ. Существенное изменение согласованного поведения фиксируй с причиной и последствиями. Сохраняй отчёт о выполненном, проверенном и оставшемся. Если нет нужной внешней машины/клиента, честно назови непроверенный пункт и подготовь точный сценарий испытания; не выдавай mocks за реальную миграцию.

В финале передай работающий код и воспроизводимый релиз, lock-файлы, миграции, OpenAPI/типы, установщики, инструкции, реальные скриншоты, результаты приёмки и конкретные ограничения. Полное определение готовности находится в последнем разделе документа приёмки.

# Размещение, перенос и восстановление Edizora

Нормативное приложение к [ТЗ](web-platform-spec.md), версия 1.0 от 25 октября 2026 года.

## 1. Гарантии и пределы

MIG-02. Плановый перенос сохраняет все подтверждённые данные, идентичность бота, очередь, историю, настройки и обязательные файлы. Он допускает остановку публикаций на всё время операции. Сроки, попавшие в паузу, могут быть нарушены по времени; их дальнейшая обработка определяется заранее выбранной политикой.

В поддерживаемой системе одновременно существует не более одного узла с правом публикации. Право выдаёт проверяемая процедура передачи, а не копия флага `active` в SQLite. Старый запуск должен оставаться запрещённым после reboot, рестарта службы и запуска прежнего ярлыка.

Гарантия относится к управляемым установкам с новым host/controller. Нельзя гарантировать отсутствие дублей, если вручную запустить старый произвольный код с тем же bot token в обход host. Перед первым промышленным запуском выявить и отключить прежние службы/ярлыки/контейнеры, способные отправлять сообщения; сохранить их как данные/архив, а не как автоматически запускаемый резерв.

Не заявлять безусловный exactly-once, нулевой downtime или автоматический failover при недоступном источнике. Потерянное подтверждение Telegram сохраняется как неопределённая отправка, даже если обе машины исправны.

## 2. Поддерживаемые установки

### DEP-01. Windows

Сохранить простой запуск из launcher. Host работает отдельно от вкладки браузера, запускает runtime и при необходимости домашний worker. Предоставить явную установку/удаление автозапуска под текущим пользователем, управляемую остановку, перезапуск и просмотр логов. Повторный запуск открывает имеющуюся панель, не создаёт второй публикатор.

Рекомендуемый каталог рабочих данных — `%LOCALAPPDATA%/Edizora/data`; программа/релизы и host state хранятся отдельно. Можно выбрать другой постоянный локальный диск. Текущую БД из папки проекта/OneDrive не переносить без плана, резервной копии и подтверждения. UNC, сетевые диски и синхронизируемые папки не являются поддерживаемым местом активной SQLite.

### DEP-02. Ubuntu

Первый автоматический установщик: **Ubuntu 24.04 LTS x86-64**, SSH, systemd, Python 3.12, выделенный непривилегированный пользователь. Профиль выбран осознанно; его срок сопровождения проверять по [официальному циклу Ubuntu](https://ubuntu.com/about/release-cycle). Не называть его «последней LTS» и не объявлять Ubuntu 26.04/ARM поддержанными без проверки.

Первый поставляемый способ — нативная служба host/controller + runtime в отдельном venv, версия программы в каталоге релиза. HTTPS reverse proxy — Caddy с ограниченной конфигурацией приложения. Допускается подключение к уже существующему reverse proxy по инструкции. Docker-конфигурация прошлого приложения не заменяет испытание нового установщика; автоматическую миграцию Docker-установок не включать без отдельного профиля.

Рекомендуемое разделение: `/opt/publisher/releases/<release-id>` — неизменяемая программа; `/var/lib/publisher/data` — переносимые данные; `/var/lib/publisher/control` — идентичность/журнал узла; `/etc/publisher` — конфигурация/секреты с ограниченными правами. Каталоги допускают изменение в расширенных настройках, после проверки принадлежности и свободного места.

Host запускается под непривилегированным пользователем; административные права нужны только установщику для пакетов, служб и proxy. Привилегированные действия — фиксированный набор операций, не произвольная shell-строка из формы. Не закрывать существующий SSH/firewall доступ и не перезаписывать чужую конфигурацию proxy. Если порт/домен занят, показать конфликт и требуемое действие.

### DEP-03. Релиз

Один перенос использует один совместимый release ID и schema version. Релиз содержит Python-код, зависимости/lock, собранный frontend, миграции, установочные шаблоны и manifest с хешами. Исходная рабочая папка имеет незакоммиченные файлы: deploy не должен молча собрать старый Git HEAD и потерять их. До переноса подготовить воспроизводимый артефакт из проверенного состояния; секреты/data не входят в кодовый пакет.

Обновление версии и перенос между узлами — разные операции. Если target требует новую схему, сначала отдельное проверенное обновление активной установки, затем перенос той же версии. Установщик идемпотентен по release ID и не скачивает/исполняет случайный latest-скрипт без фиксации источника/целостности.

## 3. Экран размещения и план

### MIG-03. Текущее состояние

Показывать отдельно место приложения, место AI, тип установки, OS/version/architecture, роль узла, активное поколение, адрес панели, bot identity, SQLite path, media root, размеры, последнюю проверенную копию и состояние публикаций. Путь — на сервере, который сейчас показан; поле не должно выглядеть как путь компьютера, где открыт браузер.

Тип «локально/сервер» задаётся профилем установки. Автоматически можно проверить ОС, путь, hostname, сетевые адреса и метаданные доступного окружения, но нельзя считать private IP доказательством локального ПК или публичный IP доказательством облака.

### MIG-04. Профиль назначения

Для VPS: имя профиля, IP/DNS, SSH port, SSH user, ключ (предпочтительно) либо пароль, способ необходимых sudo-прав, путь установки/data, внешний HTTPS URL, способ маршрутизации. Пароль панели провайдера не является SSH-паролем; мастер должен это объяснять. Покупка VM и настройка аккаунта хостинга вне приложения.

При первом соединении показать SSH fingerprint и сохранить подтверждённое доверие к выбранному узлу. При изменении ключа остановить подключение для проверки; не отключать host key checking. Проверенные профили содержат метаданные и ссылки на secret store, не открытые пароли.

Для возврата на Windows: зарегистрированный включённый локальный host, выбранная папка, достаточно места, способ исходящего получения данных и будущий внешний адрес при необходимости Mini App. Мобильный браузер не может установить службу или восстановить выключенный домашний ПК; сценарий явно ждёт локальный host.

### MIG-05. План

Сохранить plan ID/revision, source/target node IDs, system ID, source generation, release/schema, source data paths, target paths, manifest estimate, размер обязательных/опциональных файлов, доступное место с промежуточной копией и резервом, способ передачи, routing plan, AI plan, overdue policy, исходные паузы, список проверок и предупреждений.

План имеет срок актуальности (начально 15 минут) и проверяется перед запуском заново. Изменившаяся очередь не требует безусловно начинать ввод заново, но новый источник/цель, поколение, путь, релиз, объём сверх свободного места или иной существенный риск требует обновлённого плана. Финальный snapshot/manifest создаётся после остановки, а не берётся из предварительной оценки.

Проверка SSH/OS/disk/HTTPS может выполняться до начала переноса и не останавливает публикации. Установка/копирование рабочих данных в рамках переноса начинаются только после подтверждённой остановки. Несовместимую ОС, отсутствие SSH, непригодный путь или недоступный локальный host желательно выявить до паузы.

Нормативное предупреждение перед началом:

> На время переноса публикация всех постов во всех каналах будет остановлена. Начатые отправки завершатся; новые отправки, включая ручные, будут заблокированы. Очередь и настройки сохранятся. Публикации, запланированные на время переноса, могут задержаться. Работа возобновится после проверки новой установки по выбранным правилам.

Показать направления, адреса, объём и политику просрочки рядом с подтверждением. Не включать паузу от открытия вкладки или редактирования IP. Если источник уже был глобально остановлен пользователем, миграция после успеха не снимает эту независимую остановку.

## 4. Контроллер и журнал

### MIG-06. Независимое исполнение

Перенос исполняет host/controller, не HTTP request, не браузерный таймер и не публикационный worker. Закрытие Mini App/вкладки не отменяет действие. Журнал живёт в control store вне контентного снимка и записывается до необратимого шага, с устойчивым commit.

MigrationRecord: migration ID, system ID, source/target node, controller owner, generation before/after, plan revision, release/schema, current stage/state, checkpoints, snapshot hash, media manifest hash, progress sequence, activation decision/receipt, endpoints и redacted error. Установка и роли узлов сверяются при каждом восстановлении операции.

Для каждого этапа — предусловия, идемпотентный ключ, действие, доказательство результата и разрешённые действия пользователя. «Команда SSH вернулась с кодом 0» не заменяет проверку файлов/процессов/роли. Повторный start с тем же migration ID продолжает/возвращает состояние, а не создаёт вторую миграцию.

Control store и БД контента не образуют общей транзакции. Сначала сохраняется maintenance intent controller, затем закрывается gate runtime; start подтверждается только после принятия этой команды runtime. При restart незавершённый intent запрещает запуск исполнителей даже при ещё не записанном флаге в контентной БД. После ошибки между двумя commit выполняется сверка, а не предположение, что переноса не было. Снимать независимые причины gate может только их владелец/разрешённая команда.

До и после передачи управления журнал и квитанции реплицируются на назначение. На исходном узле остаётся tombstone/retired-состояние. Активный target становится точкой управления следующими операциями; не зависит от сохранённого питания старого ПК/VPS. Источник можно выключить после подтверждённого финала, не в середине передачи.

### MIG-07. Секреты

SSH credentials обрабатывает controller. Временный пароль по умолчанию только в памяти; если процесс умер, операция переходит в «Нужно повторно ввести доступ», сохраняя безопасное состояние. Опциональное сохранение ключа — защищённое хранилище ОС/приватный secret store с отдельным ключом, не открытый JSON. Не обещать автоматическое продолжение пароля после reboot, если он не сохранялся.

Передача — SSH/SFTP либо аутентифицированный TLS между зарегистрированными узлами. Пакет с секретами шифруется для цели; долговременный backup требует собственного ключа восстановления. Контрольная сумма проверяет целостность, но не заменяет проверку доверенного отправителя. Обновление публичного URL и worker endpoint не передаёт worker bot token.

Машинное secret store не копируется побайтно как универсальный файл: например, привязанные к Windows-пользователю данные не становятся читаемыми на Ubuntu. Авторизованный controller экспортирует только необходимые секреты в защищённый пакет для конкретного target, а target сохраняет их своим способом. Временный открытый материал не пишется в логи/манифест и очищается после использования.

## 5. Машина состояний переноса

Ниже — обязательная последовательность. Крупные шаги интерфейса могут объединять внутренние состояния; журнал не должен их скрывать.

| Состояние | Действия и доказательство перехода |
| --- | --- |
| `planned` | Актуальный план и явное подтверждение. Источник ещё работает по прежним настройкам. |
| `stopping` | Сохранить maintenance intent; закрыть приём новых изменений и выдачу новых send/AI permits; начать drain. UI: «Останавливаем, осталось N отправок/операций». |
| `quiesced` | Все ранее допущенные отправки завершены/изолированы как uncertain; нет активных writers; polling/inbox boundary сохранены; исполнители/cleanup остановлены. Наблюдаемые счётчики подтверждены, не просто выставлен флаг. |
| `preparing_target` | Проверить target повторно, установить тот же релиз в standby, создать отдельный staging. Нет источника данных по умолчанию «пустая рабочая БД». |
| `snapshotting` | Проверенная Backup API копия БД; финальный manifest файлов, настроек и inbox. Зафиксировать snapshot hash и schema/release. |
| `transferring` | Передача в staging с resumable file/chunk checks, реальными байтами/файлами, сохранением verified checkpoints. Оба публикатора остановлены. |
| `verifying` | Проверить хеши, SQLite integrity/foreign keys, семантическую сверку, обязательные медиа, конфигурацию, bot identity, сеть и время. Standby не отправляет посты. |
| `retiring_source` | Записать невозвратный для обычного запуска retired marker вне БД; отозвать active generation локального supervisor; остановить активный runtime и выключить его прежний автозапуск. Получить подтверждение отсутствия старого отправителя. |
| `activation_committed` | Controller устойчиво сохраняет решение передать право ровно target/generation/snapshot. Только после commit выдаёт подписанное разрешение target. |
| `activating_target` | Target устойчиво принимает разрешение, атомарно включает проверенный набор данных и запускает runtime с новой активной ролью, но с сохранённым migration gate и закрытым приёмом изменений. Возвращает квитанцию; публикации/polling/AI lease ещё не запускаются. Повтор возвращает тот же исход. |
| `routing` | Проверка HTTPS/панели, переключение предусмотренного маршрута, worker endpoint и URL кнопки при необходимости. Старый API принимает только чтение статуса и сообщает новый адрес. |
| `completed` | Target подтвердил активное поколение/readiness, необходимые адреса проверены, обязательные данные целы, итоговый отчёт/журнал доступны на target. Устойчивый финальный checkpoint разрешает снять именно migration gate с учётом прежних пользовательских пауз, открыть изменения и запустить polling/AI lease. Публикатор начинает работу только после этого допуска. |

`waiting_user`, `failed`, `cancelled`, `recovery_required` — состояния результата/ожидания поверх сохранённого этапа. В общем OperationDTO `recovery_required` отображается как `waiting_user` с соответствующим error code; исходное migration state также передаётся. Потеря связи не равна cancelled. Ошибка не снимает gate автоматически. «Все публикации остановлены» появляется только в quiesced и последующих состояниях до корректного возобновления. Если процесс упал между финальным checkpoint и снятием gate, target идемпотентно завершает этот переход после повторной проверки условий, не выдавая нового разрешения.

### 5.1. Точная граница drain/freeze

Закрытие gate сериализуется с выдачей publication permit. Уже допущенная многочастная публикация может закончиться; новая не начинается. После gate не принимаются новые правки, импорты, ручные previews и команды запуска; UI объясняет maintenance и сохраняет ещё не подтверждённый локальный ввод без отметки «Сохранено».

До freeze завершаются уже принятые транзакции, приём Telegram updates, сборка альбомов, запись статистики, финализация новостей и изменения моделей. Сначала остановить новые poll/lease, затем дождаться зарегистрированных обработчиков. Нельзя сделать снимок, пока callback/cleanup ещё может изменить файлы или БД.

Для долгого AI: попытаться дождаться результата в настраиваемое окно (начально 120 секунд). После окна показать выбор «Продолжать ждать» или «Перенести задачу и выполнить заново». Второй вариант отзывает lease, сохраняет задачу для назначения, не расходует новую пользовательскую попытку из-за самой миграции; поздний ответ не принимается. Сессия AI не переносится из середины вычисления.

При нормальном quiesced runtime может оставаться только читающим; перед выдачей права target активный исходный процесс должен быть остановлен/лишён возможности перезапуска с отправкой. Контрольный host остаётся живым. Его прогресс, сессии и журнал пишутся только в control store. Снимок контента после freeze не изменяется.

### 5.2. Манифест данных

Manifest содержит: format version; system/migration/source IDs; generation; release/schema; timestamp UTC; DB filename/size/SHA-256; количество и отсортированные ID/семантические digest обязательных сущностей; файлы с относительным ключом/размером/hash/ролью; список доступных Telegram references; опционально отсутствующие исторические файлы; inbox boundary; prepared job/readiness; настройки и их версии.

Обязательны все локальные файлы, на которые ссылаются действующие черновики и очередь. Необязательны воспроизводимые миниатюры и отсутствующий исторический архив. Если для действующего материала сохранён только remote reference, план явно показывает необходимость подготовки; queued readiness=false нельзя выдать за полностью автономную готовую очередь. Доступный Telegram file ID для того же бота может быть достаточным источником отправки; его локальная миниатюра — отдельное свойство.

Перед start мастер проверяет готовность уже подтверждённой очереди. Предложить отдельную операцию «Подготовить материалы» до переноса. Если обязательный оригинал/перевод получить нельзя, по умолчанию start заблокирован; продолжение допустимо только с явным списком удерживаемых заданий и подтверждением владельца. Эти задания переезжают целиком, получают readiness/hold reason и не запускаются на target до исправления. Потерю готовности нельзя скрыть за зелёным итогом миграции.

Переносить: ID и связи, queue_position, scheduled_at, next_publish_at, next_attempt_at, паузы/интервалы, сохранённые ручные команды, версии, историю/message IDs/части попыток, дедупликацию, receipts, inbox, черновики, AI task state, общие настройки. Не переносить как идентичность цели: source node.json, source session store, машинные абсолютные пути, активные старые lease, открытые lock-файлы, .venv, model weights.

Target проверяет `integrity_check` и `foreign_key_check`, сравнивает семантический отчёт и SHA-256 файлов. Byte hash БД сравнивается до контролируемых адаптаций путей/служебных полей; после них — новый hash и перечень разрешённых различий. Нельзя одновременно требовать одинаковые байты БД после её правки. Переход Windows → Linux проверяет разделители, регистр имён, не-ASCII и относительные media keys.

### 5.3. Активация и запрет двойного владельца

Разрешение связано с `system_id`, `migration_id`, target node ID, новым generation, hash проверенного snapshot и retired receipt источника. Подписано/передано аутентифицированным каналом зарегистрированному target. Target сохраняет решение до запуска workers и не принимает разрешение для другого node/hash.

Вначале источник прекращает активную роль; затем controller commit; затем target activation. Ни один retry не меняет назначение ранее committed разрешения. Отсутствие ACK target означает «состояние неизвестно», а не «можно снова включить источник». Query target возвращает роль, generation, migration ID и activation receipt. До получения достоверного результата оба автоматических пути возобновления закрыты.

Свежий node ID на машине с скопированной БД не становится active автоматически. Отсутствующая локальная идентичность после потери control store требует recovery. Резервная копия прошлого node state не применяется как способ обойти retired marker.

## 6. Направления

### MIG-08. Windows → Ubuntu

Локальный controller инициирует SSH-установку и передачу, остаётся жив при остановленном runtime. Target после проверки становится владельцем; локальная установка — retired/worker-only. Обычный старый ярлык показывает «Приложение перенесено» и новый адрес, а домашний worker может продолжить работу с новым API. Нельзя оставлять прежний polling/публикатор вместе с worker.

### MIG-09. Ubuntu → Windows

Windows host заранее установлен и спарен. Он получает данные исходящим соединением/SSH download; входящий публичный порт на домашнем роутере не обязателен. Облачный controller координирует передачу права и видит подтверждение локального назначения через зарегистрированный канал.

Снимок берётся с **нынешнего активного VPS**, включая новые публикации и правки после прошлого переезда. Старый локальный набор архивируется отдельно; не объединяется с новым построчно. Если ПК выключен — ожидание до начала паузы либо waiting_user, если выключился во время операции. Ни мобильный клиент, ни VPS не угадывают путь локального диска.

### MIG-10. Ubuntu → Ubuntu

Controller исходного VPS передаёт snapshot/медиа напрямую целевому VPS по SSH/SFTP/защищённому узловому протоколу. Домашний ПК не является обязательным транспортом или владельцем операции. У браузера можно закрыть вкладку; он только отображает состояние. После завершения target хранит журнал/квитанции и сам управляет следующим переездом.

## 7. Адреса, Mini App и домашний AI

### NET-01. Публичный адрес

Для локального браузера достаточно loopback HTTP. Для Mini App требуется доступный устройству HTTPS origin; localhost телефона не указывает на Windows-ПК. По возможности использовать постоянный домен, который меняет маршрут к active host. [Telegram Mini Apps](https://core.telegram.org/bots/webapps).

Мастер поддерживает подключение уже подготовленного домена/HTTPS и проверку сертификата/маршрута. Автоматическое управление всеми DNS-провайдерами не требуется. Если DNS/туннель надо изменить вручную, это явный этап waiting_user с инструкцией и повторной проверкой; migration не показывает успех заранее. Установка на IP через SSH сама по себе не создаёт HTTPS-домен.

До activation проверить целевой HTTPS endpoint, при сохранении домена — с корректным SNI/Host на target. После смены DNS проверить доступ с обычного клиентского пути; учитывать старые DNS-кэши. Старый endpoint отказывает writes, сообщает проверенный адрес active узла и не выполняет слепой redirect POST с credentials. Предпочитать повторный вход и сверку статуса команды на новом узле по idempotency key.

В обычной работе бот использует polling; webhook не нужен только из-за появления Mini App. Во время freeze/активации polling остановлен до финального допуска. Изменение URL menu button — отдельное идемпотентное административное действие через bot API, допустимое на этапе routing и не отправляющее посты. Если URL прежний, кнопку без нужды не менять. Ошибка маршрутизации/кнопки после передачи права не даёт права вернуть старый публикатор: target остаётся владельцем с migration gate до завершения проверки.

При возврате на Windows мастер предлагает: только локальная панель или сохранение внешнего HTTPS-доступа. Во втором случае требуется проверенный туннель/маршрут; его недоступность показана до старта. «Только локально» означает недоступность Mini App с телефона до повторной настройки, а не потерю данных.

### AI-02. Связь worker

Предпочтителен стабильный API URL. При его смене worker получает новое назначение по заранее спаренному защищённому каналу/подписанному redirect record, проверяет system ID и доверие к новому HTTPS origin. Не пересылает credential на произвольный URL из ответа неизвестного сервера. Если автоматическое переподключение невозможно, UI даёт короткую процедуру повторной привязки.

Отключённый домашний ПК не блокирует завершение переноса готовой очереди, если план допускает ожидание AI; финал явно показывает «AI ждёт домашний ПК». Это не считается готовностью генерации. Все начатые lease до миграции отозваны/завершены; новое поколение выдаёт их заново по правилам задач.

## 8. Просроченные публикации

SCH-01. При планировании показать ближайшие задания и выбрать политику точных дат, которые будут просрочены в конце паузы. Дефолт `catch_up`: оригинальный scheduled_at сохраняется, публикация идёт при возможности с отдельным минимальным интервалом восстановления **60 секунд на канал**; значение настраивается до старта. Этот limiter не меняет обычный интервал канала и не пересчитывает scheduled_at задним числом.

Альтернативы: `hold` — оставить такие задания на ручное решение; `skip` — отменить с явной причиной и журналом, только после подтверждения количества. Переназначение дат вручную доступно в календаре после переноса. Уже прошедшие до паузы задания также видны в списке и получают выбранную политику, а не теряются из проверки.

При catch_up eligibility=max(исходное scheduled_at, last_catchup_success+лимит), с учётом занятого/выключенного/приостановленного канала. При первом возобновлении одно просроченное задание может стать доступно сразу. Порядок по scheduled_at, затем устойчивому ID. Обычная очередь продолжает использовать перенесённый next_publish_at и свой интервал; не начинать его заново от времени reboot.

Политику применять также после длительного сна локального ПК; UI различает причину задержки. Глобальный migration gate и прежние паузы каналов независимы. Снять первый не означает снять вторые. Окончательные даты/факт задержки видны пользователю и в аудите.

## 9. Отмена, ошибки и обратный перенос

### MIG-11. Разрешённые действия

| Момент ошибки/отмены | Разрешённое поведение |
| --- | --- |
| До start | Изменить/удалить план; состояние публикаций не менялось. |
| После stop, до activation commit | Сохранить остановку. Можно повторить этап или явно возобновить источник после проверки отсутствия активированного target/разрешения и удаления готовности target к запуску. |
| Источник помечен retired, но commit ещё не произошёл | Только controller по журналу отменяет недоставленное разрешение и восстанавливает source role; обычный запуск не умеет сам снять retired. |
| Commit записан, ACK неизвестен | `recovery_required`, сверка target/журнала. Никакого автоматического rollback источника. |
| Target принял разрешение/начал работать | Источник остаётся retired. Исправить routing на target или начать новый обратный перенос его актуального состояния. |
| Источник недоступен до подтверждения остановки | Плановый перенос заблокирован. Аварийное восстановление — отдельный процесс с внешним подтверждением отключения старого отправителя. |

После activation commit интерфейс не показывает обычную кнопку «Отменить и вернуть как было». Он показывает безопасные действия текущего состояния. Не удалять исходную БД/архив автоматически. Очистка старого размещения — отдельное действие после завершения, без удаления доказательств передачи права.

Обрыв передачи: продолжить только файлы/части, проверенные по checkpoint/hash. Недостаток места/повреждение snapshot: target не активируется, частичный staging не подменяет рабочий data root. Перезапуск controller: восстановить этап из журнала, проверить реальные узлы и затем продолжить. Истёкшие credentials требуют ввода, а не снятия блокировки.

## 10. Резервные копии и восстановление

BK-01. Ручной полный backup и настройка расписания/retention в UI. Начальный предлагаемый профиль — ежедневно и 7 успешных копий; включение расписания и путь подтверждаются настройкой. Backup включает согласованную SQLite, обязательные файлы, версии/manifest, общие настройки и отдельный защищённый пакет нужных секретов. Не хранить единственную копию в той же папке, которую заменяет restore.

Для первой реализации полный backup использует краткий тот же write barrier и pin медиа; публикационные сессии корректно завершаются. Он не меняет владельца узла. Снимок делается в staging, затем barrier можно снять и копировать/проверять уже неизменяемый набор; UI показывает реальную продолжительность остановки. Финальная копия считается успешной только после verify. Retention удаляет лишь подтверждённо лишние старые успешные копии внутри настроенного каталога, не последнюю пригодную и не неразрешённые журналы.

Restore всегда начинает с плана и проверки пакета на временной копии. Проверить format/system/bot identity, schema/release, хеши, SQLite, файлы и наличие ключа секретов. Нет молчаливого слияния БД или запуска чужого system ID. Перед заменой текущего состояния сохранить его резервную копию; после restore не начинать отправки до разрешения неопределённых попыток и подтверждения владения.

Аварийный restore старой копии может не знать о постах, опубликованных после её создания. Все потенциально повторяемые задания из опасного периода пометить для сверки; нельзя автоматически поднять старую очередь и обещать отсутствие дублей. История не восстанавливается «по ощущениям» из текущего канала.

## 11. Доказательства завершения

Итоговый отчёт миграции: откуда/куда, время паузы, release/schema/system/generation, snapshot и media manifest hashes, проверки БД/файлов/ID/очереди, активная роль target, retired подтверждение source, политика просрочки и затронутые задания, состояние AI/HTTPS/Mini App, ссылка на журнал и backup. Секретов в отчёте нет.

«Успешно» не означает «все посты отправлены»: оно означает завершённый перенос и безопасное возобновление по правилам. Полная приёмка включает все три направления и отказы из [матрицы](web-platform-acceptance.md), особенно обрыв после activation commit и reboot старого узла.
